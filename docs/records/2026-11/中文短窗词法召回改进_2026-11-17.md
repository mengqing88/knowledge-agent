# 中文短窗口词法召回改进（2026-11-17）

## 结果

在本机隔离 SQLite 快照和已保存的查询向量排名上，当前 `scoped_bm25` 短窗口方案在 17 道开发题、43 条原文证据上的 Recall@12 为 **28/43（65.1%）**。上一版中文 BM25 + 向量 RRF 是 18/43（41.9%）：5 题改善、0 题退步；7 题完整覆盖全部标注。Recall@5 为 20/43，Recall@20 为 28/43，Recall@30 为 30/43。

本次直接路径重放读取 1,484 个原始块，生成 4,566 个窗口，建索引与 17 次查询合计约 6.5 秒；新模型调用和新增费用均为 0。该结果来自已经看过的开发题，不能代表独立资料泛化、答案准确率或生产效果。

## 为什么改

整块可能同时包含多个话题。问题只对应块中的一句话时，整块 BM25 会把多个话题的词频混在一起；文本越长，真正回答问题的短句越容易被无关词稀释。对短窗口计算 BM25，可以让局部用词更接近问题。

另外，中文单个字常出现在不同表达中。除二元词外加入一元词，能为“同一人物/对象、不同搭配”的表达提供部分词面交集。代价是高频单字也会引入噪声，因此 BM25 仍与向量排名融合；这批题上的提升还需要独立题集验证。

## 实现流程

1. `backend/app/knowledge/lexical.py` 把快照内原文块按句子边界切成约 160 字符的窗口；过长句子以 130 字符步长滑动，窗口只用于词法索引。
2. 每个窗口保留指向所属 `Chunk.id` 的本地映射，窗口 BM25 排名后按最高排名去重为最多 30 个原始块 ID。
3. `backend/app/knowledge/retrieval.py` 将这些块 ID 与向量排名做原有 RRF 融合。窗口文本不会作为新来源存储，也不会交给回答模型；后续仍读取、核验完整原文块。
4. 索引继续受当前快照范围、5,000 块、200 万字符上限、工作流缓存及取消检查约束。`ngram_bm25` 仍需显式选择，legacy 默认和真实 `.env` 均未改。

## 验证与边界

- `backend/tests/test_lexical_recall.py`、`backend/tests/test_runtime_lexical.py`、`backend/tests/test_retrieval_profiles.py`：16 项通过。
- 独立离线重放报告：本机忽略目录 `tmp/reports/qijin-recall-20261116/lexical-window-runtime-replay-20261117.json`；原文、标注、数据库和逐题结果未加入 Git。
- 已直接调用当前 `scoped_bm25` 实现，并与同一批已保存的向量排名融合；这不是连接 PostgreSQL/Milvus 的真实服务联调。
- 本轮没有运行 BGE 重排。当前可用内存不足以安全加载 CPU 版模型环境，不能把旧的其他题集 BGE 结果套用到本题集。
- 仍有 15/43 条标签未进入前 12；其中一部分不在 BM25 与向量并集的候选中。窗口和一元词不能解决缺少关键词、人物指代或跨段关系信息的问题。一次小样本的平均分也掩盖单题退步，不能据此开启默认配置。

## 面试复述

“我看到中文长块把不同主题的词频混在一起，整块 BM25 不容易命中段内的关键句。我在可选检索配置中改为短窗口建立 BM25 索引，再把命中的窗口映射回原文块，与向量排名融合；窗口不改变证据来源。固定的 17 题开发集上 Recall@12 从 18/43 到 28/43，但还没有独立题集或 PostgreSQL/Milvus 复验，所以保留 legacy 默认，并把单字符噪声、内存开销和泛化列为待验证项。”
