# 模型请求发送前等待的时间与权限复核

日期：2026-11-14。不修改简历、真实 `.env` 或生产服务，不发真实模型 HTTP。恢复契约保持“答案不重复发布，允许恢复后重新请求模型”。

## 已复现的问题

`backend/app/integrations/providers.py` 的 `_post` 在每轮开始时计算 HTTP timeout，之后执行重试预算登记、Redis 共享配额申请及进度记录。上述操作可能等待数据库/Redis；若此时运行截止时间或单次模型调用截止时间已过，原实现仍使用之前的 timeout 发出 HTTP。任务在这些等待期间被取消/撤权时，也只在响应后再调用 guard，不能阻止已知失效后的发送。

新增的 8 个控制用例在修复前全部失败：运行/Provider 两类 deadline × 配额/重试/进度三类等待共 6 个用例；剩余 timeout 缩减与等待期间撤权各 1 个。它们使用可推进的模拟时钟、模拟配额和 HTTP 客户端，没有真实网络或真实时间长等待。修复前的断言观察到了超期发送或仍使用 5 秒而非剩余 2 秒的 timeout。

## 修改与取舍

请求 payload 脱敏完成后、建立 HTTP 客户端之前，再执行任务 guard，并按运行 deadline 与本次 `_post` deadline 的较早值重新计算 timeout。运行已过期抛 `BudgetExhausted(time)`；单次调用窗口已过期返回 `provider_timeout`；任务失效由 guard 中止；通过时使用等待后剩余时间。

复核放在发送前，是因为循环开始时的检查不能覆盖中间等待。每次 HTTP 尝试增加一次 guard；正常 worker 中这会增加一次任务/权限读取。已申请的预算/共享配额仍按既有保守规则保留，不退款，不改变重试次数、租约恢复或发布保护。`started` 进度记录可能先于最后复核，不应把它单独当成外部请求实际到达的证明。

复核与真正发送之间仍存在时间窗口；不能原子化本地权限事务和外部 HTTP，也不能撤回已发出的请求。本轮不提供“撤权后绝无任何在途请求”、HTTP 总耗时的硬实时保证或模型调用恰好一次保证。
