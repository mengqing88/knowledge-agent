这里的“答（应包含）”是回答检查清单，不是统一的技术答案。请让对方先依据自己的源码、数据规模、部署环境和业务约束作判断，再推荐方案；说明为什么选择它、为什么暂不选其他方案，以及什么条件变化后需要重新选型。问答涵盖我提出过的修改和讨论，不等于本项目全部实现，也不表示新项目必须增加所有机制。

## 第一部分：协作、输入与工作流基础（问题 01–22）

### 一、协作方式与项目文档

#### 01. 完成功能之后，我怎样同步学懂？

**问：** 这个项目主要用于学习和面试。以后每完成我要求的功能，请在对话里解释它的目的、关键方法和参数、数据流、设计取舍及实际验证结果。请先用这个要求讲解这次改动。

**答（应包含）：** 用具体场景串起输入、处理和输出；解释为什么要加这项机制以及它的代价。例如加入熔断时，要讲清它保护哪一层、何时打开、恢复条件是什么，不能只说“提高稳定性”。

#### 02. 代码和方法应该解释到什么程度？

**问：** 请讲解我指定的代码，说明函数、类和关键变量的作用；遇到我不熟悉的方法，请解释它的参数、返回值和当前调用产生的效果。代码注释保持简洁，详细讲解放在对话里。

**答（应包含）：** 结合实际调用说明，而不是只翻译名字。本项目讨论过 `add_argument`、`Path`、`resolve`、`startswith`、`any` 和文档字符串；其他项目按实际语言和方法解释，不必照搬 Python 示例。

#### 03. 给协作智能体和简历智能体分别准备什么文档？

**问：** 请为项目维护两类 Markdown：一份介绍我的学习目标、项目目的和协作规则；另一份让简历编写智能体了解项目完成了什么、为什么这样做、有哪些评测证据和限制。

**答（应包含）：** 前者负责进入项目和协作，后者负责项目事实。事实文档应覆盖实现模块、行为变化、亮点、测试命令、真实结果、失败记录和未验证事项；后续修改要同步更新当前说明并追加日期记录。

#### 04. 修改怎样提交，怎样避免改错工作区？

**问：** 请确认本次允许修改的主工作区，保留已有改动；完成本次修改并检查后，单独提交 Git，告诉我提交号、变更范围和验证情况。不要把环境、密钥、IDE 文件或其他任务改动一起提交。

**答（应包含）：** 先核对仓库、分支和未提交内容，再精确暂存。本项目曾因主目录与额外 Git worktree 混淆产生问题；如果需要迁移改动，要先比较两边提交和差异，不能直接用其中一边覆盖另一边。

#### 05. 待做事项和“已经实现”怎样区分？

**问：** 请把我们确认的待办整理成 TODO，说明各项的目标、依赖、验收方法和当前状态。外部服务未连通、尚未运行实验的内容，不要标成已经验收完成。

**答（应包含）：** 区分待开始、进行中、本地实现完成和外部待验收。保留实现位置及可核对的验证记录；“写了适配器”“内存测试通过”“真实服务可用”是三个不同结论。

#### 06. 简历描述与代码不一致时怎么处理？

**问：** 请逐条核对项目简历描述与当前代码、配置、测试和实验记录，指出已实现、部分实现、未实现及缺少证据的内容，并给出准确的表述建议。

**答（应包含）：** 每项判断有对应实现或证据；不能验证的其他项目单独列出。目标数字、参考答案成绩和模拟结果不能冒充真实业务指标，无法证明的内容不要靠补一句宣传用语掩盖。

### 二、输入、模型接入与用户入口

#### 07. 输入限制是否来自真实业务需要？

**问：** 请检查项目对输入文件、扩展名和内容的限制。哪些是必要约束，哪些只是实现时写死的假设？如果业务需要处理代码内容而不是特定后缀，应该怎样调整并验证？

**答（应包含）：** 分清路径存在、文本编码、内容是否合法和文件名后缀。本项目曾取消“必须是 `.py` 文件”的要求；放宽后缀限制仍需保留读取范围、内容解析和错误提示。

#### 08. 用户报告不完整或与实际问题不符怎么办？

**问：** 请检查任务是否必须提供问题报告，并设计可追溯的复现记录。报告不完整时，先根据代码和证据补全；如果实际发现的问题与报告冲突，请暂停并向我提出具体问题。

**答（应包含）：** 保留原始报告、修订报告、触发步骤、实际结果和结论，不能把推测当事实。本项目曾要求每个任务生成独立的 `work/reproduction.md`；迁移时应按新项目任务隔离方式确定路径。

#### 09. 大模型和 Embedding 服务怎么配置？

**问：** 请封装模型调用，并支持聊天与 Embedding 使用不同的 Base URL、API Key 和模型名。配置放在本地环境变量或忽略提交的配置文件中，先验证接口契约与连通情况。

**答（应包含）：** 分开配置 `CHAT_*` 和 `EMBEDDING_*`，解释各变量作用、接口能力和超时错误。不能默认所有兼容服务都支持相同的 Responses、Chat Completions 或工具调用能力；未真实请求时应明确写未连通验证。

#### 10. 模型返回的 JSON 和代码块解析可靠吗？

**问：** 请检查模型输出解析是否依赖固定的 Markdown 围栏、字符串切片或猜测格式。围栏长度或语言标记变化、JSON 缺字段、格式不合法时会怎样？请修复明确缺陷并验证。

**答（应包含）：** 输出约定、解析规则、结构校验和有界纠错保持一致。本项目曾出现动态生成围栏却只剥离固定三反引号的问题；应验证真实输入变体，避免静默截错或把失败当成功。

#### 11. 用户入口真的接通了工作流吗？

**问：** 请检查命令行或界面是否真正启动完整业务工作流，而不是仅调用模型或展示假数据。如果改成界面，请保持简单，接通创建任务、查看进度、查看结果和审核操作。

**答（应包含）：** 解释 CLI 是程序入口而非命令行窗口本身，给出真实运行方式。界面技术根据新项目决定；本项目使用过 Vue 3、TypeScript、Vite，重点是与后端真实状态一致。

### 三、工作流与自主工具调用

#### 12. 应该用 LangGraph、LangChain，还是简单编排？

**问：** 请根据这个项目的状态管理、分支、循环重试、人工暂停和恢复需求，比较 LangGraph、LangChain 与直接编排方案，给出推荐及理由，不要因为已有某个依赖就默认它最合适。

**答（应包含）：** 区分组件封装与状态图编排，不把两者说成只能二选一。推荐要对应实际复杂度和维护成本；简单任务可以采用更简单的实现，不能为了技术名词制造流程。

#### 13. 状态对象与完整工作流有什么区别？

**问：** 请画出当前实际流程，说明状态对象有哪些字段、节点做什么、条件边如何跳转、哪里暂停。只有一个状态文件或一次 LLM 调用，是否已经形成完整工作流？

**答（应包含）：** 用真实入口和节点说明执行路径，区分“记录数据”与“驱动流程”。标清失败、预算耗尽、需要澄清、待人工审核和已完成等状态，不把待审核写成成功结束。

#### 14. 怎样实现真正的 ReAct 工具循环？

**问：** 请检查当前 Agent 是否能根据工具返回结果决定下一次调用。如果只是固定调用一次模型，请实现受约束的“模型决策—工具执行—返回结果—继续决策”循环，直到产生最终结果或触发停止条件。

**答（应包含）：** 工具调用消息与结果正确关联，模型能看见真实返回，最终结果有明确契约。自主决策仍受权限、预算和验证节点控制，不能把允许循环理解为允许任意执行。

#### 15. 工具参数怎样由程序强制校验？

**问：** 请用 Pydantic 或当前技术栈的 Schema 校验机制统一工具参数，检查必填字段、严格类型、空字符串、数值范围和额外字段，并让模型看到的参数定义与执行规则一致。

**答（应包含）：** 校验发生在执行之前，返回具体字段错误并允许有界纠正。结构合法不代表业务授权成立；路径、任务归属和金额等业务限制仍需独立检查。

#### 16. 模型能调用写工具，为什么还要固定验收节点？

**问：** 如果允许模型主动修改内容、应用补丁或运行测试，请明确它能操作什么；最终交付前，再由固定节点核验最终结果。请说明模型试验结果和正式验收结果怎样关联。

**答（应包含）：** 工具注册不等于放开所有权限。模型中途运行的测试不能替代最终验收；验收证据应绑定最终补丁或产物版本，避免验收了 A 却交付 B。

#### 17. 预算和死循环上限分别限制什么？

**问：** 请说明一次完整任务、一次修复尝试和一次工具调用的区别，分别设置最大尝试次数、总运行时间、Token 和费用上限，并指出检查与扣减发生在哪里。

**答（应包含）：** 本项目曾使用 10 次修复尝试、120 秒、20,000 tokens、0.10 元，以及单轮 30 次工具调用；这些是本项目参数，其他项目应重新估算。费用与 Token 相关但还依赖单价；调用次数不等于修复轮数，等待人工的时间也要明确口径。

### 四、执行副本、测试与人工确认

#### 18. 当前操作的是原版还是任务副本？

**问：** 请检查复现、修改和测试分别在哪个目录、哪个版本执行。能否从指定 commit 或输入快照创建任务副本，使整个任务使用一致基线，避免修改原始项目？

**答（应包含）：** 说明 commit 固定的是哪份内容，未提交改动是否包含在内。复现基线、补丁应用和最终验收之间应能对应，不能在一个版本复现，却在另一份未核对的目录计分。

#### 19. 失败或拒绝后能否真正恢复？

**问：** 请检查修改失败、测试失败或人工拒绝后，是否恢复任务副本到上一个明确 checkpoint；验证新增、删除及修改文件是否都正确处理，并保留必要记录。

**答（应包含）：** 区分工作流状态 checkpoint 与代码文件快照，恢复状态不等于恢复文件。副本恢复不得覆盖原项目或其他任务；远端 API 已产生的副作用也不能靠本地 Git 回滚。

#### 20. 验收标准是否只靠提示词保护？

**问：** 请禁止 Agent 修改、删除或弱化验收测试及相关执行配置。不要只在提示词里说“别改测试”，请在写入范围、补丁检查和实际执行层落实保护并验证绕过场景。

**答（应包含）：** 保护实际收集的测试和会改变测试行为的配置，隐藏验收与可修改内容隔离。要能证明最终运行的还是原验收标准，否则“测试通过”可能只是把断言改松了。

#### 21. 怎样证明目标问题修好了？

**问：** 请根据本次缺陷报告、源码和实际复现，自动形成专用 pytest 或本项目测试框架的回归用例，让它先在旧版本中因目标问题有效失败，再验证修复后通过，同时运行既有测试和原复现。如何避免仅凭现有测试或几个示例通过就认定结果正确？

**答（应包含）：** 收集错误、依赖缺失或语法错误不能冒充成功复现。补充边界和兼容性检查，必要时单独审查硬编码结果、接口变化等风险；模型审查仍不能代替独立测试。

#### 22. 接受和拒绝结果分别怎么记录？

**问：** 请在最终验收后加入人工确认。接受后再沉淀成功经验；拒绝时询问并保存理由，恢复任务副本，且不要把拒绝案例当成成功方案。

**答（应包含）：** 审核绑定当前产物版本，旧页面不能批准新结果。记录接受、拒绝及理由来源；拒绝理由是用户反馈，只有经过证据验证才能认定为技术错误事实。

## 第二部分：工具、RAG 与记忆（问题 23–39）

### 五、自定义工具与 MCP

#### 23. 哪些能力应该封装成工具？

**问：** 请梳理模型需要的能力，说明哪些适合按需工具调用，哪些必须由固定节点执行。工具描述、参数语义、前置条件和依赖关系应该怎样设计，才能减少误选和误调用？

**答（应包含）：** 本项目涉及读取、搜索、经验检索、应用补丁、运行测试和保存经验。其他项目按业务替换；保存已验收知识等动作可由固定节点控制。工具 Schema 注册与“将工具文本向量化检索”是不同机制，不能混称 Skills Embedding。

#### 24. 有哪些外部工具目录，哪些值得接入？

**问：** 请查找适用于该项目的 MCP 工具目录和官方服务，评估维护者、权限、实际能力、费用与数据流，推荐真正有用的服务，并说明哪些能力仍应保留自定义实现。

**答（应包含）：** 从项目缺少的能力出发，例如文档、仓库与 Issue、错误事件上下文。目录上架不代表可信；通用工具不能自动继承项目的修改范围、测试保护和 checkpoint 规则。

#### 25. 怎样做可配置的通用 MCP 客户端？

**问：** 请支持配置外部 MCP 服务，说明本地 stdio 与远程 Streamable HTTP 的连接方式、工具发现、命名冲突处理、参数校验、超时和缺少凭据时的行为。

**答（应包含）：** 每个服务显式配置允许工具，凭据从环境引用，动态 Schema 也需校验。分别记录已实现配置、发现到工具、真实调用成功，不能用一个配置模板证明服务已接通。

#### 26. 外部写工具如何授权，失败后能否重试？

**问：** 请区分只读工具与会产生外部影响的工具。对外部写操作，如何绑定具体用户、任务、工具和完整参数进行审批，并防止改参数、重复调用或超时重试造成重复副作用？

**答（应包含）：** 参数或配置变化重新授权，幂等键关联同一次业务动作。写后响应丢失属于结果未知，要先查回执或人工核对；“请求超时”不能直接推出“没有执行”。

### 六、RAG 与向量数据库

#### 27. 应该选什么向量数据库？

**问：** 请分析常用的向量数据库和向量检索工具，对比 Qdrant、PostgreSQL + pgvector、Milvus、Chroma、FAISS 等方案。先核对本项目已有数据库、预计数据量、向量维度、更新频率、过滤与隔离需求、部署环境，再用表格比较，给出当前阶段的推荐、备选方案及理由，并说明什么条件下值得迁移。

**答（应包含）：** 先区分数据库、扩展和检索库，再比较元数据过滤、租户隔离、更新删除、持久化、备份运维、全文/混合检索能力及与业务正文的一致性。推荐要对应真实约束，缺少规模或负载信息时明确假设，不能编造性能排名。本项目讨论后选择过 Qdrant 作为向量索引，正文仍保留在业务数据库；其他项目可得出不同结论，不能把历史偏好当成实测最优。性能比较的验证要求见 28。

#### 28. 怎样验证向量库选型，而不是只列优缺点？

**问：** 请为候选向量库设计公平对比，固定语料、向量、过滤条件和查询，测试检索正确性、延迟、写入更新、内存或资源使用及维护成本。明确哪些能本机测，哪些必须连接真实服务。

**答（应包含）：** 相同向量和查询配置下，单纯更换存储通常不等于语义模型质量提高。内存客户端、模拟适配器只能验证相应逻辑，不能当作真实服务性能、并发和运维对比；测试限制应随结论一起记录。

#### 29. 文档应该怎样分块？

**问：** 请先分析本项目是否需要长文档分块调优：当前资料有多长、查询粒度是什么、是否已经发生截断、跨段漏召回或上下文浪费？需要时再比较按标题/段落、语义、函数或固定长度分块，分析 chunk 大小、overlap 和父子块检索的取舍，提出可验证的调整方案。

**答（应包含）：** 以实际长度分布和失败查询判断是否值得做，保留来源、版本、章节/函数边界和父文档关系。比较不同切分配置对召回、重复内容、最终任务成功率和 Token 的影响。短修复案例可能整体检索更合适；不能只给一个通用长度就宣称优化，也不能把字段拼接直接称为已经做过分块实验。

#### 30. 向量文本里是否混入了无关内容？

**问：** 请分别检查查询文本和入库文本，减少日志、堆栈重复、补丁 diff、无关路径等内容对向量的干扰，同时保留完整原文供追溯。修改文本规则后，旧向量如何更新？

**答（应包含）：** 优先保留问题表现、根因、适用条件与必要上下文，区分向量文本和完整证据。给嵌入规则及模型版本留痕；只修改新文本生成代码，不会自动修正已有向量。

#### 31. 成功经验和失败经验会不会抢召回名额？

**问：** 请把成功经验与失败或拒绝经验分别召回，设置独立名额并明确标记。如何让失败经验帮助避坑，而不是挤掉有效成功案例或被误当作推荐答案？

**答（应包含）：** 存储、查询和展示都有结果类型，后续模型指令区分正向方案与反例。失败原因、适用范围和证据需保留，不能只添加一个 `rejected` 字段就认为已经解决名额竞争。

#### 32. 语义相似但环境不一致的案例怎样过滤？

**问：** 请为检索增加业务范围过滤，例如用户、业务线、仓库、文件路径或依赖版本。任务指定过滤条件而旧案例缺少对应元数据时，比较宽松与严格策略，并给出推荐。

**答（应包含）：** 身份规范化和版本匹配口径明确，过滤在何处执行可核对。本项目选择过严格过滤：缺少所需元数据的旧案例不召回，代价是降低召回量，需要补齐元数据；新项目应明确自己的容错要求。

#### 33. 如何处理不同 ID 下语义重复的案例？

**问：** 请检查完全重复和语义近重复数据，区分“检索结果折叠”与“持久化合并”。如果高相似案例需要合并，请保留来源与原始内容，并验证误合并、索引同步和阈值变化后的行为。

**答（应包含）：** 相似度不是唯一条件，先检查用户、结果类型及适用范围。主案例关系可追溯，不把相反结论合并；本项目曾采用 0.97 阈值，但其他语料应评测误合并率，不能直接照抄。

#### 34. Cross-Encoder 重排是否值得做？

**问：** 请比较向量相似度排序、Cross-Encoder 重排和 LLM 重排的效果、延迟、费用与部署要求，分析本项目是否值得增加重排。如果采用，请比较不同初召回数量和重排数量，并说明模型不可用时怎样回退。

**答（应包含）：** Cross-Encoder 联合处理查询与候选，能检查更细的匹配关系，但仍有计算与模型依赖成本。5–10 是本项目讨论过的候选规模，应通过召回与重排评测调整，不能保证所有项目都最优。

### 七、短期记忆、长期记忆与反馈

#### 35. 对话越来越长，记忆怎么管理？

**问：** 请区分工作流状态、短期对话历史、个人偏好和长期案例知识，比较滑动窗口、摘要以及向量检索记忆，设计适合当前项目的组合，并解释 Token 和连贯性的取舍。

**答（应包含）：** 明确每类数据保存在哪里、何时写入、何时读取和是否需要审核。摘要可能遗漏或误写事实，向量检索可能不命中；不能因为保存了聊天历史就宣称所有长期记忆能力已经具备。

#### 36. 失败经验真的会影响下一次决策吗？

**问：** 请跟踪失败信息从产生、保存到下一次模型调用的完整路径。当前任务上一轮的错误和其他任务长期保存的拒绝经验，分别如何进入下一次决策，怎样验证没有只是存了却没用？

**答（应包含）：** 用实际状态、检索结果和模型请求上下文证明数据到达。区分本任务重试反馈与跨任务长期召回；反例应帮助避免重复错误，不应成为未经核验的业务真相。

#### 37. 什么资料可以进入正式知识库？

**问：** 请检查成功结果、拒绝理由、外部导入案例和对话提炼内容的入库条件。哪些必须人工确认，哪些能根据可信系统证据发布？不确定时怎样进入待审区而不是直接参与检索？

**答（应包含）：** 发布绑定内容版本和来源，区分通过测试、人工接受、模型自报与上传文件声明。审核代理的结论仍需服务端检查；拒绝补丁和拒绝收录外部资料是不同事件，不能混为失败经验。

#### 38. 记忆能否持久化、清理并隔离不同用户？

**问：** 请检查会话和长期记忆是否能跨重启保存，设计过期清理与用户、业务线隔离，验证越权查询、更新、删除和账号切换。数据库应根据项目需要选择，不要直接照搬 Java、Redis 或 MySQL 方案。

**答（应包含）：** 服务端身份决定数据范围，不能信任模型或请求自行声明租户。说明会话过期、消息留存、长期偏好删除的区别；正文库隔离与共享向量 collection 的过滤都要验证。

#### 39. 资料过时、被修改或被删除以后怎么办？

**问：** 请检查知识正文、向量索引、摘要和当前任务引用之间的版本关系。内容修改、合并、删除或模型切换后，如何避免继续检索到旧向量或让历史任务结果悄悄变化？

**答（应包含）：** 正文主存储与向量投影职责清楚，更新和失败补偿可追踪。当前任务需要复现时应冻结语料快照；新版本重建与旧任务读取不能混淆。

## 第三部分：异步、安全、评测与 Agent 架构（问题 40–65）

### 八、异步、限流、熔断与恢复

#### 40. 项目真的做到异步了吗？

**问：** 请沿接口、任务调度、模型调用、工具执行和数据库访问检查阻塞点，说明哪些适合异步、线程池或后台 worker。加入合理并发与排队上限，避免流量增加时把请求无限堆积。

**答（应包含）：** 不能只把函数写成 `async`；同步网络、数据库、文件及子进程仍可能阻塞。解释入口限流、worker 并发和上游服务配额各保护什么，并验证拒绝或排队行为。

#### 41. 模型超时和响应延迟怎样兜底？

**问：** 请分别设计单次请求超时、工具执行超时和整个任务截止时间，说明取消、超时后保留哪些状态，以及什么时候能安全失败、什么时候必须暂停核对。

**答（应包含）：** 子调用受剩余总预算约束，超时错误有分类且可追溯。停止等待不代表底层操作已经停止；有副作用的请求结果未知时，不能直接启动下一次相同操作。

#### 42. 熔断和降级应该加在哪里？

**问：** 请根据模型、Embedding、检索库及外部工具的故障传播路径设计熔断和降级，解释失败阈值、冷却、恢复探测和状态共享范围，优先保障核心业务。

**答（应包含）：** 说明每种故障下还能提供什么，例如向量检索不可用时退回关键词。不能在验收、鉴权或关键写入失效时伪造成功；是否跨请求、跨进程或跨重启累计故障需要明确。

#### 43. 重试与模型死循环怎么控制？

**问：** 请区分网络瞬时错误重试、参数纠错、修复重试和重复无效工具调用，分别设置上限。如何处理 429、退避等待和相同调用反复失败，避免越重试负载越高？

**答（应包含）：** 只对可安全重试的错误执行退避，并计入总预算。未知工具和参数错误交回模型有限纠错；连续重复无进展要停止或暂停，不能只有一个很大的统一循环上限。

#### 44. 崩溃、重启和重复请求会不会重复执行？

**问：** 请检查任务状态落库前后崩溃、写成功但响应丢失、重复点击及旧 worker 回写等场景，设计幂等、持久操作记录和恢复规则。副作用前审计记录写不进去时怎么办？

**答（应包含）：** 写入意图、执行状态和回执能核对，旧执行不能覆盖新状态。关键审计失败时停止相应副作用；对已完成返回原结果，对未知结果先查询或人工处理，不盲目重放。

### 九、安全边界、流式体验与可观测性

#### 45. 如何处理提示注入与越界业务请求？

**问：** 请检查用户输入、源码、检索文档和 MCP 返回中的恶意指令，明确允许业务范围，并在模型和工具边界前实施权限检查。如何验证模型即使服从恶意内容，也不能执行越权动作？

**答（应包含）：** 不可信资料只能提供数据，不能自授权限、伪造系统消息或批准记录。业务范围、身份、工具权限、路径及外部写审批分别由程序校验；不能把安全性寄托在一句提示词上。

#### 46. 临时目录与 Docker 隔离分别解决什么？

**问：** 如果项目要执行生成代码或外来代码，请比较任务副本与容器执行的保护边界，检查文件挂载、网络、资源限制、敏感目录和清理，并验证真实执行环境。

**答（应包含）：** 临时目录防止混用源码，但不是 OS 安全沙箱；有 Docker CLI 也不等于 Engine 和容器任务可用。还要说明 MCP 或宿主工具是否绕过容器，以及容器不能回滚哪些远端操作。

#### 47. 密钥和敏感信息会通过哪些路径泄露？

**问：** 请检查文件读取、代码搜索、模型请求、Embedding、工具定义、错误日志、Trace 和 Git 历史中的敏感信息路径，设计统一保护并验证别名或绕过场景。

**答（应包含）：** 配置密钥仅用于认证，不混入提示词；敏感路径不能只检查表面字符串。脱敏、权限和日志保留分别设计，明确通用脱敏识别的局限，不能宣称能够识别一切未知凭据。

#### 48. 用户看到的“流式输出”到底是什么？

**问：** 请区分模型逐 Token 输出与任务进度、工具事件流，选择适合当前项目的展示方式，并设计断线重连、断点续传、取消和账号切换后的清理。

**答（应包含）：** SSE、WebSocket 或轮询按需求选择，不把后台步骤轮询描述成逐字模型流。状态事件来自真实执行，取消展示与取消服务端任务的含义清楚，连接权限不能只在建立时检查。

#### 49. 怎样留痕、回放并监控整个链路？

**问：** 请为每个任务关联模型请求、可见输出、工具参数、结果、重试、审核和错误，设计可追溯日志与核心指标。区分只读回放和重新执行，记录重现所需的配置和版本。

**答（应包含）：** 保存可获得的消息和决策摘要，不虚构模型内部思维记录。冻结模型参数、提示词、工具 Schema、环境、知识库和预算；回放不触发外部副作用，重新执行创建独立任务。指标与告警需要真实采集和规则，只有日志不等于已有监控告警。

### 十、评测、回归与上线验证

#### 50. 样例仓库和参考答案本身可靠吗？

**问：** 请建立或整理样例任务，先验证原实现通过既有测试且目标验收有效失败，再验证参考补丁通过固定测试。保留原始来源、文件哈希、修订理由和失败结果。

**答（应包含）：** 检查任务与经验 ID、补丁路径、相关性映射及不同来源格式。参考补丁成绩只能证明题目有效，不是 Agent 成绩；不通过改断言、删题或忽略收集错误凑结果。

#### 51. 数据划分和答案泄漏如何防止？

**问：** 请检查数据来源、使用权限和复核状态，按仓库、时间或缺陷家族划分开发、验证和冻结测试集，审查近重复任务，并隔离隐藏验收、参考补丁和相关性标签。

**答（应包含）：** 只给 Agent 当前题允许读取的内容，控制其文件、工具、检索及 MCP 访问范围。不同 ID 不代表不同问题；不能把当前题答案写进检索库，也不能虚构审核者或把未复核候选集标成正式集。

#### 52. RAG 优化效果应该怎样评测？

**问：** 请为关键词、向量、混合、过滤、去重和重排设计对照，统计 Recall@K、Precision@K、MRR 及误召回情况，再检查检索变化是否改善最终任务成功率和成本。

**答（应包含）：** 标签来源与独立性明确，同时报告无关、范围冲突和失败经验等场景。检索命中率上升不必然提高修复率；需要固定模型、预算和任务，分别运行关闭与开启 RAG 的真实产物对照。

#### 53. 模型或工具升级怎样判断是否退化？

**问：** 请在升级前固定任务、配置差异、重复次数和门槛，比较工具契约、参数语义、必要行为、最终验收、成本与延迟。如何避免平均分提高却掩盖关键任务从成功变失败？

**答（应包含）：** 保留逐题配对及所有重复结果，单独检查关键分组、安全硬失败和费用证据。接口返回成功不等于副作用正确，需核验实际业务回执；不能挑最好一次重跑或只看 Schema 通过。

#### 54. 压测、灰度和回滚真的做到了吗？

**问：** 请检查项目在高峰流量、慢模型、429、数据库不可用和 worker 故障下的行为，制定回归、压测、分批发布与快速回滚的验证方案，说明当前已有证据和未完成部分。

**答（应包含）：** 负载、资源、并发、失败率与延迟口径固定，验证核心路径及恢复。配置回滚还要考虑数据和索引兼容；测试通过不等于已灰度上线，方案、合成演示和真实部署分开报告。

#### 55. 最终应把哪些结论写回项目？

**问：** 请把本次需求、实现与取舍、验证命令、原始分子分母、失败原因和限制写回项目记录，并明确下一步。所有尚未验证的内容请列出，不要只写“全部通过”。

**答（应包含）：** 区分代码检查、单元测试、模拟服务、合成任务、真实服务和端到端结果；不能简单累加重叠测试。记录应让另一位智能体能找到证据，帮助你据实改简历并讲清项目。

### 十一、业务边界、架构与模型选型

#### 56. 这个项目为什么需要 Agent？

**问：** 请根据本项目的真实任务，分析哪些步骤需要模型动态决定下一步，哪些用固定工作流、检索、规则或普通函数就够了。比较纯规则、固定工作流加模型、单 Agent、多 Agent 的收益和代价，给出当前阶段的推荐及理由。

**答（应包含）：** 举出需要根据中间结果改变行动的具体例子，说明不用 Agent 时如何完成。不要把一次文本生成、参数校验或定时任务都称为 Agent；选择应基于任务不确定性、错误代价、维护成本和已有证据。

#### 57. 哪些动作能自动执行，哪些必须停下来问人？

**答（应包含）：** 相同任务、验收标准和环境下比较，报告样本量与失败任务。不能只统计模型生成速度而忽略重试、人工修正和失败恢复，也不能把目标收益写成已经取得的效果。

**答（应包含）：** 比较工具调用、结构化输出、上下文长度、延迟、价格和服务稳定性；给出任务路由依据与升级条件。微型 Agent 可以表示受限职责，不代表已经使用独立小模型；模型名、价格与能力需有当时可核对的来源，不能凭印象排名。

**答（应包含）：** 审查核对实际基线、最终产物和版本哈希；确定性检查与模型证据审查职责清楚。引用不存在、证据不足或审查器不可用时不能当作通过。说明误拦截和额外调用成本，模型审查仍不是正确性证明。

**答（应包含）：** 审核 Agent 无权执行导入内容中的工具指令；服务端独立核对任务归属、验证记录、产物哈希和验收决定。模型自报置信度不能替代证据。区分模型建议、人工终审和实际发布权限；不能把无法确认直接写成最终拒收。

## 第四部分：反馈、预算、Trace 与评测治理（问题 66–85）

### 十三、拒绝反馈、知识发布与失败回归

#### 66. 用户拒绝时，应该问清什么？

**问：** 请检查拒绝结果时是否询问并保存理由，能否区分用户偏好、事实错误、执行失败、遗漏场景、需求变化和当前无法完成。如何保存原话、分类依据与不确定项，又不让用户每次重复描述？

**答（应包含）：** 保留反馈来源、对应产物版本和已有证据。用户说“不满意”不直接证明技术错误；含糊反馈提出具体澄清，不能靠模型猜一个原因，更不能因此把已拒绝结果记成成功知识。

#### 67. 拒绝经验怎样变成长期回归用例？

**问：** 请设计“保存拒绝理由—脱敏—分类—生成测试—隔离复现—审核发布—后续任务使用”的闭环。如何证明生成的是有效反例，哪些反馈不能自动生成技术断言，验证失败以后保留什么？

**答（应包含）：** 分清两种方向：验证原缺陷修复时，旧版应因目标缺陷失败、修复后通过；验证补丁破坏原有正常行为时，基线应通过、拒绝补丁应失败。依赖、收集或语法错误不能冒充行为反例。未经验证和审核的候选不进入正式回归集，也不直接成为成功经验。

#### 68. 怎么避免审核了 A，却发布了 B？

**问：** 请检查审批绑定的是哪份内容。如果生成的测试、验证报告、补丁或导入正文在人工查看后发生变化，旧批准能否继续使用？请设计版本或内容哈希检查，并验证旧页面和并发修改场景。

**答（应包含）：** 哈希应覆盖被批准的完整对象；失败回归至少包括反馈、测试内容和验证证据，外部写授权包括具体工具与参数。服务端在执行或发布前核对，变化后重新审核；不能只绑定任务 ID 或原始反馈。

#### 69. 修复应该落在提示词、知识库、工具契约还是业务流程？

**问：** 请根据这次失败的实际证据定位根因，比较修改提示词、补充知识、修正工具 Schema/适配器、调整状态流与验收的作用，推荐最小有效修复及理由，不要遇到任何问题都先加提示词。

**答（应包含）：** 缺事实资料检查知识，误用工具检查描述与契约，权限漏洞落到程序检查，漏步骤或错误恢复检查工作流。一次问题可能跨层，但要说明每层承担的责任，并用相同失败案例复测，避免多处同时改后无法归因。

#### 70. 后续模型或向量服务失败，会不会丢掉拒绝记录？

**问：** 请沿拒绝处理的数据流检查：理由保存、失败案例写入、向量化、回归生成、发布和索引更新，哪些必须先持久化？中途崩溃或外部服务不可用时，如何查到原反馈并安全补做？

**答（应包含）：** 原始反馈先落盘，状态区分待处理、待人工、已验证、已发布与失败；重复请求有稳定身份。正文保存、向量索引可用、回归已发布是不同结论。明确后台重试是否真的实现，不能只因存在一个重试方法就声称已有自动闭环。

### 十四、请求预算、并发与缓存

#### 71. 能否在发请求之前就控制 Token 和费用？

**问：** 请检查 Token 和费用是否只在模型响应后核算。如何在聊天、工具调用和单条/批量 Embedding 发送前估算输入、限制输出并拒绝明显超预算的请求？重试和结构纠错是否也消耗同一预算？

**答（应包含）：** 说明估算方法、误差、供应商实际用量和单价来源，输出上限随剩余额度变化。缺价格、缺 usage、请求成功但响应丢失时保留未知状态，不能用零费用代替未知费用；估算护栏不自动等于供应商账单的精确硬上限。

#### 72. 预算耗尽后，返回部分结果、降级还是请求继续？

**问：** 请根据本项目不同任务和执行阶段，设计预算耗尽时的处理：哪些证据可以作为部分结果返回，哪些可安全降级，哪些必须暂停并请求追加预算。请分别说明时间、Token、费用、工具次数与尝试次数耗尽的行为。

**答（应包含）：** 部分结果注明已完成和未完成；降级不得跳过鉴权、正式验收或伪造成功。先停止并核实在途操作，不能预算归零后仍在后台产生新副作用；人工等待与执行消耗的计时口径明确。

#### 73. 追加预算怎样做到不重置历史、不重复加钱？

**问：** 请分析预算耗尽任务是否可以安全续跑，设计归属校验、理由、额度上限与幂等请求键。重复点击、重启或响应丢失后，如何保证只增加一次额度？哪些状态必须禁止直接续跑？

**答（应包含）：** 初始冻结预算不被覆盖，追加记录与任务更新可靠落盘。仅复用仍有效的证据，从明确节点继续；未知工具结果、旧 worker 未停止、未清理执行环境等先处理。追加预算不等于自动重放外部写操作。

#### 74. 哪些步骤适合并行，排队和领取任务如何配合？

**问：** 请检查本项目任务内部与任务之间的依赖，列出可并行和必须顺序执行的步骤。怎样配置 worker、排队和上游配额，避免先领取大量任务却无法执行，或让多个角色同时改同一份内容？

**答（应包含）：** 只读独立检索可能并行，共享写入、依赖前一步产物和需要授权的动作受约束。容量检查、领取身份、旧 worker 回写保护和锁范围可核对；并发度应结合 CPU、内存、数据库和模型配额压测，不能只把 worker 数调大。

#### 75. 哪些结果可以缓存，缓存如何失效？

**问：** 请分析本项目适合缓存的代码分析、Embedding、检索、工具结果和模型结果，逐项说明缓存键、范围、有效期、更新条件与不可缓存的内容。知识库、代码版本、模型或工具契约变化后怎样避免复用旧结果？

**答（应包含）：** 缓存键考虑账号/权限、源码与资料版本、模型、提示词、工具参数和 Schema；失效可以依赖版本或内容哈希，不能只靠一个固定 TTL。外部状态、审批和未知副作用不能靠缓存当作当前事实；报告命中率、延迟收益与过期错误，而不是只证明缓存里存了数据。

### 十五、配置冻结、Trace 与环境诊断

#### 76. 某次任务使用的完整配置能否查出来？

**问：** 请为单次任务设计不可变执行清单，检查是否保存应用代码身份、待处理源码基线、依赖/容器、模型及生成参数、提示词正文和哈希、工具 Schema 与权限、知识库快照、用户记忆、原始输入、初始预算及实际执行证据。

**答（应包含）：** 区分任务创建时冻结、首次工具发现时记录、执行过程中追加的证据。密钥只记录凭据引用；追加预算、审核和工具回执单独留痕，不改写原清单。环境变量或知识库后续变化不能悄悄改变在途任务。

#### 77. 记录回放和重新执行是同一件事吗？

**问：** 请分别设计只使用已保存响应的记录回放，以及再次调用模型和工具的重新执行。它们各能定位什么问题，需要哪些产物，工具证据缺失或存在未完成调用时应该怎样报告？

**答（应包含）：** 回放不触发真实外部副作用，不能用模型重新生成缺失记录冒充历史。重新执行使用独立任务与操作身份，外部写授权按实际边界重新核验。相同配置仍可能因模型采样、供应商和外部状态不同产生不同输出。

#### 78. 有 commit 和哈希，是否就能重建当时环境？

**问：** 请检查依赖是否真正锁定、镜像是否固定 digest、模型是否有可获取版本，以及应用未提交改动是否另有保存。执行清单记录与自动重建环境还差哪些能力？请给出可验证的重建或限制说明。

**答（应包含）：** 哈希用于识别和比对，不能恢复丢失文件；commit 不包含未提交内容。供应商只给模型别名时记录未知，不能虚构版本；缺少锁文件、镜像或源码副本时明确不能完整还原。区分修复服务版本与待修复仓库的 checkpoint。

#### 79. 完整 Trace 具体应该记录到哪一层？

**问：** 请逐层检查工作流、Agent 回合、ReAct 循环、模型请求、工具执行、验证、重试、审批和终止原因，哪些事件只在内存中使用，哪些已持久化。能否沿同一任务还原每次可见请求、结果和状态变化？

**答（应包含）：** 任务、节点、调用和产物版本能关联，调用开始/结束及异常可配对，敏感字段脱敏。关键副作用前审计落盘失败时阻止对应执行，不能先做后补日志。记录可观察输出和决策摘要，不把模型内部不可见思维当作完整 Trace 的必需产物。

#### 80. 端口启动失败与业务执行失败怎样区分？

**问：** 请根据实际错误和当前系统解释服务为什么无法绑定端口，区分端口占用、系统保留范围、权限或地址配置，与代码业务异常、模型超时之间的关系。请先给出可验证的诊断步骤，再推荐适合本环境的处理方法。

**答（应包含）：** 以真实错误码、监听信息和操作系统配置为依据，说明服务是否已启动、前端应连接哪个地址。换端口需检查后端、代理和前端配置是否一致；不能仅凭某个端口号就断言被占用，也不要未经依据修改系统权限或防火墙。

### 十六、可验证评测、真实验收与版本治理

#### 83. Docker/worktree 隔离怎样做真实端到端验收？

**问：** 请用样例任务在真实 Git worktree 和 Docker Engine 上跑完整流程，验证原始源码不变、复现与测试真实执行、敏感/Git 信息不泄露、验收挂载只读、网络与资源受限、超时后无遗留进程或容器，并检查产物能否返回宿主。

**答（应包含）：** 分别记录命令、Engine/镜像身份、环境、产物及清理结果。可以固定模型回复来单独验证执行层，但需明确模型是模拟的；Docker 命令拼接单测不等于容器验收，Engine 预检失败就记 blocked，不能跳过后续步骤仍算通过。真实接口可用后还需验证完整生产入口。

#### 84. 提示词、模型、知识库和工具变更怎样上线与回退？

**问：** 请分析本项目是否对模型、提示词、工具接口与权限、知识库/Embedding 索引、工作流和容器分别版本化，设计离线回归、配对升级验证、灰度范围、停止条件和回滚方法。总成功率变高但关键场景退化时如何处理？

**答（应包含）：** 发布记录能还原版本组合；逐题结果、安全硬失败、成本和延迟门槛在实验前确定，不要求合理调用顺序完全一致。回滚要考虑数据结构与索引兼容、在途任务和旧授权；只有方案或合成演示时不能声称已经完成真实灰度。具体升级行为检查结合 53。

#### 85. 修改完成后，怎样核对相关路径和最终差异？

**问：** 请完成我明确要求的修改后，重新运行原复现、验证旧实现失败的回归，再检查相关调用路径、最终差异和文档。新保护规则导致旧测试失败时，怎样区分实现缺陷、测试桩过期、环境故障和真实行为退化？

**答（应包含）：** 找到失败原因再决定改实现还是改测试；不能为了全绿放宽权限、删断言或替换隐藏验收。最终报告列出实际修改、运行命令、结果、未验证项和遗留改动；单次全量与重叠专项不简单相加，代码审查也不能替代重新执行原复现。

## 第五部分：当前项目的具体改进题（问题 86–106）

### 十七、从本项目具体需求提炼的改造题

#### 86. 演示界面怎样接上真实 Python 工作流？

**问：** 如果界面目前展示固定补丁、假进度，接受或拒绝只存在浏览器内存，请沿前端、Python API、工作流、持久化存储和页面刷新完整检查。请设计改造方案，并验证创建任务、流式查看、接受、拒绝及重启后的状态恢复。

**答（应包含）：** 先确认真实 API 和节点实际存在，再明确每个 UI 操作对应的请求、身份校验和持久化字段。前端不能自行宣称补丁已验证或接受；接受应绑定已验证的补丁版本，拒绝理由应保存。用 API/工作流测试验证持久化，不以截图或静态 mock 证明已连接。

#### 87. 怎样在模型调用之前挡住业务范围外的请求？

**问：** 请先与我确认允许的业务范围；如果仅允许软件开发，是否涵盖代码生成、解释、审查、调试和测试设计？请把明显越界和无法确认范围的输入在聊天、任务、CLI 等入口挡在模型、Embedding 和 MCP 之前，同时检查编码偏好等正常表达不会被误拒。

**答（应包含）：** 门禁放在第一个可能触发模型或外部服务的边界之前，服务端决定，不依赖提示词自律。用正反例验证“单独提到语言名”不会放行、明确编码偏好可进入软件场景、同一消息里的越界请求仍被拒绝。规则分类器有误判边界，需说明规则覆盖和未覆盖表达，不能称作通用语义证明。

#### 88. 指令不清楚时，怎样澄清而不是猜？

**问：** 请区分越界请求、缺少关键业务信息、模型输出契约不完整和工具失败。对仍在业务范围内但目标或验收条件不足的请求，怎样记录缺失字段、生成具体问题、暂停后等待用户补充，再从合适节点继续？

**答（应包含）：** 澄清状态应是可持久化的流程结果，包含原因和用户能回答的问题；不能把模型猜测写成用户要求。模型 Schema 错误可以有限次反馈修正，业务信息缺失应向用户询问，权限错误不能靠重生成绕过。拒绝越界请求应发生在模型调用之前。

#### 89. 多个工具冲突时，怎样确保没有先执行一部分？

**问：** 请检查模型能否在一轮提出多个工具调用、工具功能是否互斥，以及多个任务是否会写同一外部资源。设计冲突组、资源锁和整批预检，并验证冲突批次不会出现“前一个工具已执行，后一个才被拒绝”。

**答（应包含）：** 执行前一次性检查工具白名单、角色权限、全部参数、冲突组和资源范围；任一失败则整批不执行。资源锁键要稳定覆盖服务端点及资源身份，不同配置别名不能绕过同一资源锁。说明哪些冲突需要配置者声明，不能声称系统能自动理解所有工具语义。

#### 90. 参数不合法时，模型纠错与服务端拒绝怎样分工？

**问：** 请用 Schema 校验必填字段、类型、范围和额外字段，再在执行前检查用户身份、业务约束、路径和工具权限。参数错误能否返回具体字段问题让模型有限重生成？哪些错误必须拒绝或询问用户，不能原样重试？

**答（应包含）：** Schema 负责结构，服务端负责授权和业务不变量；Schema 通过不代表操作符合用户意图。把可修正的格式错误与权限不足、越界、业务冲突、结果未知分开。为纠错轮次设上限，并验证无效参数和越权请求没有触发副作用。

#### 91. 怎样把各层故障都变成可追踪、可诊断的错误？

**问：** 请沿浏览器、API、队列/worker、模型、Embedding、数据库、MCP、Docker、文件操作和 Trace 存储建立故障清单。统一哪些结构化字段、错误编号、因果链、用户提示、下一步操作和脱敏规则？Trace 本身写失败时如何报告并保护关键副作用？

**答（应包含）：** 区分错误类别、是否可重试、结果是否未知、请求/任务/操作关联 ID 和底层原因；敏感值不能进入用户响应或日志。对关键副作用采用写前审计，审计落盘失败就不执行。用故障注入逐层验证错误被保存、可按 ID 查询且没有泄漏秘密；只记录日志不等于已有告警。

#### 92. 超时后哪些请求能重试，哪些结果必须先核对？

**问：** 请区分模型只读请求、Embedding、代码测试、数据库事务和外部写工具。对连接失败、429、部分 5xx、参数错误、权限拒绝及超时分别设计有限重试、退避、`Retry-After` 和熔断；超时但操作可能已完成时怎样查询状态？

**答（应包含）：** 只对明确可安全重放的瞬时错误重试，且受次数和总时间预算限制。参数或权限错误应修正请求或拒绝，不能原样重试。写操作先复用同一幂等键；结果未知时查询回执或暂停人工核对，不能把客户端超时等同于服务端未执行。

#### 93. 用户账号、会话和业务权限应该怎样分层？

**问：** 如果需要用户名密码注册、登录和退出，请设计密码哈希、会话轮换、Cookie、CSRF、防暴力尝试和账号切换处理。如何保证任务、聊天、诊断、知识库和个人记忆都由服务端身份隔离，而不是信任请求中的 user_id？

**答（应包含）：** 身份认证回答“是谁”，授权回答“能访问什么”，二者不能混为一个客户端字段。验证未登录、跨用户 IDOR、CSRF、退出后会话失效、重复请求和限流；数据库路径或查询过滤必须由已验证会话推导。不能把密码保存为明文或写进日志。

#### 94. 聊天摘要与从聊天提炼的个人记忆有什么区别？

**问：** 请设计最近对话窗口、滚动摘要和长期记忆候选。模型能否从聊天中提出用户偏好、编码规范或长期事实？如何让用户查看、修改和确认候选，保存来源对话和时间，并避免候选直接覆盖既有记忆？

**答（应包含）：** 摘要服务于当前对话连续性，长期记忆跨会话复用，两者应分开存储和更新。模型只提出候选；程序做脱敏、类型校验和账号隔离，用户确认后再写入。记录来源、用户修改和冲突；说明摘要遗漏、错误提取和敏感信息识别的局限。

#### 95. 旧任务和记忆要迁给哪个账号，怎样迁？

**问：** 如果历史任务和长期记忆原先没有用户归属，请先确定唯一迁移账号，再设计停服检查、备份、幂等迁移、迁移后校验和回滚。初始密码怎样安全交付，怎样避免写进代码、Trace 或 shell 历史？

**答（应包含）：** 迁移对象、目标账号和冲突处理必须明确，不能按“当前登录用户”猜归属。执行前备份并记录数量/哈希，迁移后核对所有权和跨用户不可见；初始凭据一次性交付或强制重置，不保存在源码、日志和文档。旧格式与新格式的并存窗口和恢复办法应说明。

#### 96. `run_id` 和 `revision` 分别防什么问题？

**问：** 请为可恢复的后台任务分别定义 worker 执行身份和状态版本：哪个用于隔离旧 worker，哪个用于检测旧快照覆盖新状态？检查领取、节点提交、恢复和重新启动时服务端如何验证这两个值。

**答（应包含）：** `run_id` 标识一次执行/租约，用于 fencing，旧 worker 即使继续运行也不能提交或执行受保护副作用；`revision` 是状态版本，用于 compare-and-swap，阻止基于旧状态的更新覆盖新版本。它们不是租户或用户身份，也不能证明外部副作用结果。说明版本递增时点、并发冲突和重启后的新旧身份测试。

#### 97. 恢复过程自身又中断，怎样回到恢复开始前？

**问：** 请设计两阶段恢复：开始恢复前保留可信检查点 A，恢复修改只写到隔离目标 B；全部证据验证后再提交。若恢复中途崩溃或回滚也失败，怎样从 A 幂等重做，并避免旧 worker 同时回写？

**答（应包含）：** 明确准备、应用、验证、提交和回滚状态，持久记录阶段与内容哈希。恢复本身失败应保留 A 和审计，不把半成品说成已回滚；重复恢复须幂等并验证文件清单。先确认旧 worker/容器停止，恢复时预算、审计和副作用记录不能通过倒退快照抹掉。

#### 98. 证据不足、查询失败或内容冲突能交给微型 Agent 吗？

**问：** 请分析是否需要独立只读诊断 Agent 帮忙补充证据、检查参数冲突和查询恢复状态。它能否提出下一步查询，哪些情况必须暂停并交给用户或人工？如何防止微型 Agent 自行制造证据、放宽权限或确认外部副作用已完成？

**答（应包含）：** 微型 Agent 可以整理已有证据、发现矛盾并建议只读查询，但不能把证据不足变成“已完成”，也不能自行批准或执行未知写操作。保留原始事实、引用和不确定原因；权限、状态结论和副作用核对由服务端规则或人工决定。模型建议不是操作回执。

#### 99. “回滚”到底能恢复哪些文件和业务数据？

**问：** 请把本项目每一种副作用逐项列出：任务工作区文件、本地数据库记录、知识库、远程 MCP 服务或邮件/订单等外部业务数据。分别说明能否恢复、怎样验证以及需要什么补偿操作；哪些必须让用户事前逐项确认？

**答（应包含）：** checkpoint 只证明项目控制范围内的快照可恢复，不能撤销第三方已提交的操作。外部操作需要状态查询、幂等或业务补偿；补偿本身也是副作用，可能再次需要审批。按具体操作逐项确认，不给“整个任务可回滚”的笼统保证。

#### 100. “预算耗尽”具体是哪一种预算？

**问：** 请把总运行时间、模型 Token、估算费用、工具调用数、请求重试数和修复尝试数分别核算、持久化和展示。哪一个耗尽时停止哪些节点，哪些清理仍必须完成？UI、API 错误、Trace 和审计记录是否使用同一个明确标记？

**答（应包含）：** 错误应携带稳定的预算类别和用户可理解标签，不能全部显示同一句“预算耗尽”。说明初始额度、扣减依据、未知用量及跨恢复保留方式；费用估算不能冒充供应商账单。达到预算后阻止新的可选工作，但不能因此跳过必要的进程清理、状态落盘或安全恢复。

#### 101. 流式请求没收到最终 usage，费用和 Token 怎么算？

**问：** 请分别分析流在收到部分内容前中断、生成已完成但最终用量尚未持久化、进程在收到 usage 后崩溃这几种情况。如何保存请求身份和计费证据，何时标为“用量未知”，怎样对账且避免恢复时重复扣减或重复调用？

**答（应包含）：** 没收到最终 usage 时不能从文本长度伪造精确 Token 或费用，应保留未知标记和请求/供应商关联信息。请求前可预留上限，收到 usage 后先持久化，再提交最终任务状态；崩溃窗口要有去重与对账方案。若供应商无法查询且本地没有证据，明确保留不确定性，不能把未知改成零。

#### 102. checkpoint 回滚与运行预算怎样计时？

**问：** 请明确一次任务的总截止时间是否包含停止进程、清理容器、恢复 checkpoint 和核对外部状态。比较共用一个 wall-clock 截止时间与保留独立清理额度的方案；预算耗尽时仍需恢复，如何避免安全清理被预算分支跳过？

**答（应包含）：** 说明每类耗时是否计入用户任务预算、Token/费用是否会因回滚改变，以及清理预留的硬上限。已消耗资源不能因回滚恢复；安全收尾也不能无限运行。将正常执行截止、停止等待和清理截止分开记录，并测试预算恰好耗尽和清理超时。

#### 103. 什么叫“真实 MCP 写入”，人工审批批准了什么？

**问：** 请用项目中的具体工具解释只读 MCP 与真实 MCP 写操作的区别。若操作会在远程服务创建、修改或删除数据，审批界面要展示哪些信息，批准是否绑定工具、端点、资源、完整参数和幂等键？超时后如何处理结果未知？

**答（应包含）：** MCP 是调用协议，不自动等于只读；是否写入由工具行为和配置策略决定。审批只授权一项明确操作，不等于第三方保证安全，也不表示项目能撤销它。参数、端点或资源改变应重新审批；响应丢失先核对状态，不盲目重试。即使用户允许真实端点，也不能宣称绝不影响业务。

#### 104. 怎样把“不能影响主业务”转成可验证的保护目标？

**问：** 请把“异常立即切断链路、绝不影响主业务”拆成可实现的边界：只读与写入权限、隔离执行、限时、限流、熔断、故障时降级、人工批准、监控和回滚。哪些能通过架构保证，哪些只能降低风险，哪些第三方行为无法由本系统保证？

**答（应包含）：** 把保证写成可测试的不变量和故障场景，不做“任何情况下零影响”的绝对承诺。核心权限由服务端执行，隔离与容量限制由运行环境提供，审计/告警覆盖可观察路径；获批外部写操作仍可能产生真实影响，checkpoint 不具备远端事务回滚能力。

#### 105. 模糊指令、工具冲突、超时和参数错误怎么做验收？

**问：** 请为这四类线上风险分别设计正常、边界和故障注入用例：模糊指令能否先澄清，冲突工具能否整批拒绝，超时后是否核对未知结果，Schema 错误能否有限纠正？请给出指标、门槛和证据格式。

**答（应包含）：** 分别度量澄清正确/误暂停、冲突拦截及零副作用、重试次数和未知结果处理、参数首次通过率及纠错后通过率。安全错误单独作为硬失败；模拟 MCP/模型结果与真实沙箱接口测试分开。模型自报成功不能作为验收，需要 Trace、操作回执和独立断言。

#### 106. 怎样把改动讲清楚并同步项目事实？

**问：** 每次改代码后，请说明改动解决什么问题、为何放在这一层、数据如何流过入口/服务/存储、权限与失败边界、主要取舍、关键参数及实际验证结果。哪些改动要同步到项目现状文档，怎样标出模拟、真实服务和未验证项？

**答（应包含）：** 用本次真实模块和数据流解释，不用代码注释替代讲解。同步当前实现说明和带日期的变更记录，保留旧失败证据；测试命令必须来自实际运行，标明跳过/失败、模拟与真实服务前提。没有验证的效果和生产安全保证应明确写未验证。
