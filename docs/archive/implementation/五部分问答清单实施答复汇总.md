### 原题全文

- **01. 完成功能之后，我怎样同步学懂？** 这个项目主要用于学习和面试。以后每完成我要求的功能，请在对话里解释它的目的、关键方法和参数、数据流、设计取舍及实际验证结果。请先用这个要求讲解这次改动。

- **02. 代码和方法应该解释到什么程度？** 请讲解我指定的代码，说明函数、类和关键变量的作用；遇到我不熟悉的方法，请解释它的参数、返回值和当前调用产生的效果。代码注释保持简洁，详细讲解放在对话里。

- **03. 给协作智能体和简历智能体分别准备什么文档？** 请为项目维护两类 Markdown：一份介绍我的学习目标、项目目的和协作规则；另一份让简历编写智能体了解项目完成了什么、为什么这样做、有哪些评测证据和限制。

- **04. 修改怎样提交，怎样避免改错工作区？** 请确认本次允许修改的主工作区，保留已有改动；完成本次修改并检查后，单独提交 Git，告诉我提交号、变更范围和验证情况。不要把环境、密钥、IDE 文件或其他任务改动一起提交。

- **05. 待做事项和“已经实现”怎样区分？** 请把我们确认的待办整理成 TODO，说明各项的目标、依赖、验收方法和当前状态。外部服务未连通、尚未运行实验的内容，不要标成已经验收完成。

- **06. 简历描述与代码不一致时怎么处理？** 请逐条核对项目简历描述与当前代码、配置、测试和实验记录，指出已实现、部分实现、未实现及缺少证据的内容，并给出准确的表述建议。

- **07. 输入限制是否来自真实业务需要？** 请检查项目对输入文件、扩展名和内容的限制。哪些是必要约束，哪些只是实现时写死的假设？如果业务需要处理代码内容而不是特定后缀，应该怎样调整并验证？

- **08. 用户报告不完整或与实际问题不符怎么办？** 请检查任务是否必须提供问题报告，并设计可追溯的复现记录。报告不完整时，先根据代码和证据补全；如果实际发现的问题与报告冲突，请暂停并向我提出具体问题。

- **09. 大模型和 Embedding 服务怎么配置？** 请封装模型调用，并支持聊天与 Embedding 使用不同的 Base URL、API Key 和模型名。配置放在本地环境变量或忽略提交的配置文件中，先验证接口契约与连通情况。

- **10. 模型返回的 JSON 和代码块解析可靠吗？** 请检查模型输出解析是否依赖固定的 Markdown 围栏、字符串切片或猜测格式。围栏长度或语言标记变化、JSON 缺字段、格式不合法时会怎样？请修复明确缺陷并验证。

- **11. 用户入口真的接通了工作流吗？** 请检查命令行或界面是否真正启动完整业务工作流，而不是仅调用模型或展示假数据。如果改成界面，请保持简单，接通创建任务、查看进度、查看结果和审核操作。

- **12. 应该用 LangGraph、LangChain，还是简单编排？** 请根据这个项目的状态管理、分支、循环重试、人工暂停和恢复需求，比较 LangGraph、LangChain 与直接编排方案，给出推荐及理由，不要因为已有某个依赖就默认它最合适。

- **13. 状态对象与完整工作流有什么区别？** 请画出当前实际流程，说明状态对象有哪些字段、节点做什么、条件边如何跳转、哪里暂停。只有一个状态文件或一次 LLM 调用，是否已经形成完整工作流？

- **14. 怎样实现真正的 ReAct 工具循环？** 请检查当前 Agent 是否能根据工具返回结果决定下一次调用。如果只是固定调用一次模型，请实现受约束的“模型决策—工具执行—返回结果—继续决策”循环，直到产生最终结果或触发停止条件。

- **16. 模型能调用写工具，为什么还要固定验收节点？** 如果允许模型主动修改内容、应用补丁或运行测试，请明确它能操作什么；最终交付前，再由固定节点核验最终结果。请说明模型试验结果和正式验收结果怎样关联。

- **17. 预算和死循环上限分别限制什么？** 请说明一次完整任务、一次修复尝试和一次工具调用的区别，分别设置最大尝试次数、总运行时间、Token 和费用上限，并指出检查与扣减发生在哪里。

- **18. 当前操作的是原版还是任务副本？** 请检查复现、修改和测试分别在哪个目录、哪个版本执行。能否从指定 commit 或输入快照创建任务副本，使整个任务使用一致基线，避免修改原始项目？

- **19. 失败或拒绝后能否真正恢复？** 请检查修改失败、测试失败或人工拒绝后，是否恢复任务副本到上一个明确 checkpoint；验证新增、删除及修改文件是否都正确处理，并保留必要记录。

- **20. 验收标准是否只靠提示词保护？** 请禁止 Agent 修改、删除或弱化验收测试及相关执行配置。不要只在提示词里说“别改测试”，请在写入范围、补丁检查和实际执行层落实保护并验证绕过场景。

- **22. 接受和拒绝结果分别怎么记录？** 请在最终验收后加入人工确认。接受后再沉淀成功经验；拒绝时询问并保存理由，恢复任务副本，且不要把拒绝案例当成成功方案。

### 代码修复数据流与设计理由

### 问答答案审核数据流与设计理由

主问答仍先完成 Planner、检索、分析、Verifier 和确定性引用检查。默认配置 `ANSWER_REVIEW_REQUIRED=true` 时，发布节点保存候选答案后把 run 置为 `review_pending`，并停止 worker；这是因为 Verifier 与 Analyst 都来自同一自动化系统，不是独立业务负责人。审批门禁放在发布前，能保留自动核验的技术结果，同时不让待审文本出现在阅读者界面。

管理员/编辑者通过审核队列读取论点及原文，接受或拒绝。接受写 `answer_approval_records` 和 `accepted_answer_experiences`，哈希覆盖答案及引用内容；发布 API 每次读取都重算，哈希不一致则拒绝提供。拒绝要求理由并保存原答案摘要；发起人 replay 时创建新 run、沿用相同文档快照、将理由放入新问题。旧 run/answer/trace 保持原状。这样拒绝是可追溯的修订输入，不会覆盖历史，也不会把拒绝的答案沉淀成成功经验。

阅读者在待审时只能看见“待人工审核”状态，不能通过 run、answer、evidence、feedback、trace 或 recording API 取到正文/引用/草稿。管理员/编辑者可查看队列并审核。设置 `ANSWER_REVIEW_REQUIRED=false` 只适合隔离评测或自动回归；该开关冻结进执行清单，防止运行中配置变化造成同一 run 的发布语义漂移。

这会增加人工等待、审核队列和迁移表，因此它与代码补丁审批、MCP 外部写入审批分别记录。问答审批不修改源文档，也没有“回滚文档副本”；拒绝后的修订是新问答 run。

创建任务时，服务解析仓库相对路径并限制在 `CODE_REPOSITORY_ROOT` 下，拒绝脏工作树，再将用户给定的 Git ref 解析成 commit ID。固定 commit 能保证复现、补丁和测试针对同一版本；detached worktree 把写操作隔离到当前用户的单个任务副本，避免覆盖源仓库和其他任务。

生成补丁时，模型只接收用户选定的已跟踪 Python 源文件及目标描述。服务校验统一 diff 的路径、选中文件范围和保护名单，再用 Git 原子检查/应用补丁。测试目录、`conftest.py`、pytest/构建依赖和 CI 配置不能通过模型补丁修改。把这项保护放在 API/补丁执行边界，是因为提示词本身不能阻止恶意或格式异常输出。

验收时，服务先在宿主临时目录复制固定提交与已应用补丁中的已跟踪普通文件，剔除凭据目录和敏感文件，再以固定镜像 ID 启动本机 Docker。容器使用 `--network=none`、只读根文件系统、只读工作区挂载、非 root 用户、移除 capabilities、no-new-privileges、512 MiB 内存、1 CPU、64 PID 和 300 秒超时。这样限制的是测试进程的可见数据、网络和资源；它不证明任意主机 Docker 配置都安全，也不替代目标项目依赖兼容性验证。

补丁哈希只表示文件改动版本，测试证明摘要还绑定基线 commit、目标、选中文件、摘要、固定命令、镜像/环境、测试退出码和输出哈希。审核前会重算两者；任何版本改变都要求重新验收。拒绝记录先持久化再清理，避免文件清理失败导致人工理由丢失。接受时才写入带补丁哈希的经验记录；拒绝理由是用户反馈，不会被当作已证实的根因。

评测汇总中，首查询 Hit@5 每个有标签问题只取首 attempt、首轮、第一条请求，缺失也留在问题分母，不能把补检或重试叠加成更多样本。费用按每题记录价估算，只在所有题都有完整价格与用量、且币种一致时相加；否则总费用是 `null`。这两个约束避免分母膨胀和把美元、人民币当成同一金额。

### 25. 通用 MCP 客户端：用户确认后已实施

用户选择“本轮新增客户端基础能力”。已加入官方 Python MCP SDK 1.30 与 jsonschema，实现在 `mcp_client.py`、`extensions_api.py`。支持 stdio 和 Streamable HTTP；服务配置为管理员本地 JSON，精确限制用户、知识库和工具，凭据仅从环境引用，默认关闭。工具发现不等于业务调用成功。

服务配置包含稳定 server_id、transport、端点或 command/args、环境变量引用、显式工具白名单和超时。只读策略由本地配置声明，不信任远端 readOnlyHint 自动授权。参数校验拒绝外部 Schema 引用；没有自动 OAuth 登录或请求重试。

- stdio：后端启动明确配置的本地进程，协议占用 stdin/stdout，诊断走 stderr；最小环境传递，不把整个 `.env` 交给进程。
- Streamable HTTP：后端连接明确端点；凭据从环境读取。服务端身份、组织权限与本项目用户范围应明确映射。
- 工具发现：列举完成后按白名单筛选，用 server_id + 原始工具名形成无歧义身份；动态 JSON Schema 在调用前验证，禁止模型修改连接参数。
- 缺配置、缺凭据、参数非法、超时：执行前返回明确错误；没有回执不能宣称成功。默认关闭，不把探测成功当成实际业务调用成功。
- 验证分三层：配置/策略单测，本地协议进程联调，指定真实服务的发现与调用。需分别留下证据。

### 26. 外部写工具：审批与结果未知机制已实施

用户选择“本轮新增审批与结果未知处理机制”。已实现本人操作提案、摘要审批、执行、回执、事件和人工核对接口，数据持久化；没有连接邮件、订单或真实文档写工具。MCP 和写开关默认关闭，真实业务服务仍需另行指定。

实现先保存候选操作，摘要绑定 user_id、run/attempt、任务配置、端点/服务配置及凭据指纹、原始工具名、Schema、完整参数、目标资源和幂等键；用户批准后，执行前重新校验这些字段及实时编辑权限，变化须新提案重新审批。幂等键对应同一次业务动作，不能随重试变化。原子领取执行、提交审计后才发出调用，一个提案最多发送一次。

进程失联或回执存储失败可保留 executing，超过 150 秒后读取详情保守转 unknown；只有 unknown 可以登记本人核对证据，标记为 manual_resolution。供应商专用状态查询未实现，不能把用户核对冒充远端回执。五张新表通过 `0006_tools_memory` 迁移，保留原 `0005_code_repair`。

### 27. 向量存储选型

当前业务存储目标是 PostgreSQL 17 + pgvector，正文、版本、权限及索引记录在同一业务数据库。SQLite 只承担教学/测试路径。历史模型为 4096 维，当前自动维度由实际返回确认；更换模型不等于只改 collection 维度即可。

| 方案 | 类型 / 部署 | 过滤、更新、隔离与一致性 | 当前取舍 |
| --- | --- | --- | --- |
| PostgreSQL + pgvector | 数据库 + 向量扩展 | SQL 约束和事务便于关联正文、版本、权限及过滤；内建全文可融合，备份随数据库 | 推荐保留；当前精确余弦路径无需新服务。4096 维及所选表示能否建立具体 ANN 索引需按实际扩展版本验证，不能承诺直接加 HNSW |
| Qdrant | 独立向量数据库 | payload 过滤、向量集合和更新能力；正文库之外需维护投影、删除与补偿 | 若真实规模/过滤压测证明单库不满足，可作首个独立备选；增加服务和双写一致性负担 |
| Milvus | 向量数据库系统 | 大规模检索及标量过滤，需规划 collection/partition、删除可见性与运维 | 当前样本和部署条件不足以支持增加其运维成本 |
| Chroma | 嵌入式/服务化向量存储 | 便于原型，隔离、备份和过滤行为需按部署模式验证 | 适合独立实验；当前业务库已承担持久状态，迁移收益未证实 |
| FAISS | 检索库 | 进程内索引，权限、元数据过滤、持久化、更新和并发需应用另做 | 适合离线候选实验，不能直接替代有权限和版本的业务数据库 |

迁移触发条件应是：真实语料和目标并发下，既定检索延迟/资源/维护预算不达标，且候选方案在相同过滤语义下有可复测收益。用户尚未提供真实规模或 SLA，因此不虚构门槛或性能名次。本轮没有迁库。

### 28. 公平对比怎样做

本次 `docker info --format '{{.ServerVersion}}'` 失败：找不到 dockerDesktopLinuxEngine 管道。没有启动、下载或创建任何服务，不能报告 PostgreSQL/Qdrant/Milvus 的服务性能成绩。

候选实验应冻结以下输入，再运行真实服务：

1. 语料 ID、正文 SHA-256、向量模型/维度/规范化方式、同一份预计算向量，以及独立查询集；向量生成耗时与存储检索耗时分开。
2. 共同的余弦语义、top-k、知识库/版本过滤及应排除的越权记录。先测精确检索并对齐结果；ANN 另测相对精确基线的召回和参数。
3. 相同硬件与并发；冷/热分开，预热次数、重复次数、P50/P95、吞吐与资源峰值同时记录。随机化方案执行次序，保留超时和失败分母。
4. 批量写入、单条更新、删除、重启持久化、备份恢复，以及正文成功但向量失败等故障注入。明确何时查询可见。
5. 越权命中必须为零；其他延迟、资源和质量门槛在取得业务要求后、实验前固定。输出逐查询原始结果和配置，不只输出汇总排名。

本机可先做向量距离/过滤的确定性测试、实验数据与校验器。内存客户端或 SQLite 成绩只能说明该路径，不替代服务并发、持久性和运维对比。本次没有新造一套向量库适配平台。

### 29. 分块是否需要调优

已有规则按页/章节组织约 3200 字符块，长原文以 2200 字符分段，小末块可重叠。教学库目前最大 Chunk 仅 389 字符；其漏答案例不能归因于长块截断。

| 方案 | 适用场景 | 代价 / 验证重点 |
| --- | --- | --- |
| 当前页/章节 + 字符上限 | 可解释定位、资料规模尚小 | 页边误删属于实现缺陷，本轮修复；不调整长度参数 |
| 标题/段落边界 | 真实手册有稳定层级和跨段流程 | 测跨段必要证据是否完整、章节与来源是否保留 |
| 语义分块 | 主题混合、固定长度已证明破坏语义 | 额外模型/依赖和不确定性，需冻结模型及版本 |
| 父子块检索 | 小块召回精确但缺上下文 | 父块增加输入；需限制扩展范围并验证跨版本隔离 |
| 函数/语法块 | 源代码知识检索 | 当前不是源码修复产品，没有必要直接套用 |

后续实验先收集真实文档长度分位数、跨边界失败题和必要证据，再比较 Recall、重复比例、答案覆盖/错误率、实际 Token 与耗时。没有这些证据不称作已经完成分块优化实验。

### 30. 向量文本清理与旧向量

查询来自 Planner/Verifier，并去重；正文嵌入 Chunk.text，原始 SourceBlock.text 单独保留。没有把 Trace、异常堆栈、补丁 diff 或用户反馈拼进向量文本。不能为清理“噪声”而删除否定、数字、条件或对原文有用的代码块。

旧清理的具体问题：相同句子在三个页边出现后，程序对所有同文字块都跳过；同页重复三次也被当成跨页页眉。本轮仅排除“确在页边且在至少三个不同页重复”的块，正文同句保留。两项合成回归先在旧实现失败，再在修复后通过；未声称真实材料 Recall 提升。

规则变化已提升 CHUNK_CONFIG，指纹仍包含 Embedding 地址/模型/维度/revision。旧库没有自动迁移或重新付费向量化。用户需要使用新规则时，走已有 reindex 接口，等索引成功后创建新快照；原快照和历史答案继续保留来源。

### 31. 成功与失败经验的召回名额

当前资料检索仍是团队文档。用户确认后，新增独立的 MemoryEntry 成功/失败经验，不把 ReviewRecord 或历史 trace 自动向量化。两类经验按服务端用户身份分别查询，每类候选池最多 100、分别最多选 2 条，避免一类挤掉另一类。采用轻量关键词/中文双字匹配，并非记忆向量检索。

经验必须关联本人已结束任务，经本人确认后才能跨任务使用；附来源、类型、版本、确认状态与文档 manifest 范围。失败仅作风险提示，不能变为制度证据。用户反馈不自动转换经验；当前名额为有界实现参数，未经过真实质量评测。

### 32. 相似内容的业务范围过滤

当前两路检索都先限制 Chunk.index_revision_id 为快照白名单，再排名；快照由已验证成员身份和当前可用文档版本构建。ScopedTools 不接受模型自行传入 owner_id、知识库或替换快照。

本项目的严格边界是知识库、文件/解析/索引版本和运行归属；没有仓库版本兼容或业务线实体。目录/标签当前用于文档选择，不是新增权限层。缺所需版本不能召回；不以“语义很相似”为理由回退到其他知识库。已有双路白名单、跨库/撤权和私人运行测试，本轮补充非法参数不进入 Embedding 的验证。

如果以后增加业务线/依赖版本，应服务端规范化元数据，先讨论缺失值策略。权限字段缺失必须拒绝；相关性字段可否放宽需用户确认业务规则。

### 33. 重复与合并

当前同一逻辑文档相同文件 SHA-256 上传被拒绝；RRF 按 Chunk ID 去重；多查询候选按 Chunk 聚合；EvidenceSpan 按运行/块/字符范围去重。它们都不是跨文档语义合并。

不同文档或版本中的相似段落可能表达相反条件。推荐先保留来源、必要时仅折叠展示，暂不持久化合并。若真实冗余明显，应先在人审集测误合并率，要求同权限域、类型与适用条件一致，保留 canonical 关系及全部原文；不直接套用 0.97 阈值。本轮没有删除或合并资料。

### 34. 重排的选择和失败行为

当前是全文/向量各最多 30 → RRF 每查询最多 12 → 跨查询文档平衡池最多 24 → 聊天模型选相关原文块。不是 Cross-Encoder。

| 路径 | 优点 | 代价 / 现有证据 |
| --- | --- | --- |
| 向量/RRF 排序 | 少一次聊天调用，路径简单 | 排名不保证回答相关性；教学运行有标题挤占结果的历史反例 |
| Cross-Encoder | 联合处理问题与候选，适合细粒度相关性 | 需独立模型、算力和语言适配，尚未部署或实测 |
| 当前 LLM 重排 | 可结合多子问题和来源块选择，沿用现有服务 | 增加聊天耗时/费用；现有模拟回归不证明真实效果提升 |

推荐当前保留已实现路径，后续固定候选输入，再比较“无重排、LLM、具体 Cross-Encoder”；候选/输出数量至少覆盖 12/24/更大候选池对成本及覆盖的影响，不能先认定 5–10 最佳。具体实验规模应随真实题集决定。

重排模型不可用时，当前 run failed，保留检索记录，不发布答案；可由用户明确选择 baseline_rag 创建新运行。没有静默改模式。新增故障注入测试证明重排错误不会形成发布答案；真实服务故障未联调。若以后要自动降级，需先确定界面标记、保留哪些质量保证及独立验收标准。

### 35. 四类记忆的现状

| 数据 | 保存/读取方式 | 当前边界 |
| --- | --- | --- |
| 工作流状态 | QuestionRun.state、事件、模型/检索记录；worker 更新 | 用于当前任务控制和追踪，不是用户偏好 |
| 短期指代上下文 | 追问关联 parent_run_id，最多四条前问进入 Planner | 仅用于明确指代；不能当作业务证据；固定窗口可能遗漏更远前文 |
| 个人偏好 | MemoryEntry 候选 → 本人确认；新任务最多选 4 条 | 只影响表达；模型不自动提炼、保存或确认 |
| 长期经验 | MemoryEntry 按成功/失败分别召回、冻结并传 Planner/Analyst | 同用户、知识库、文档快照；只作提示，不成为文档事实 |

滑动窗口实现成本低但会丢远处信息；滚动摘要更省 Token，但会遗漏/误写且需要版本与重算；向量记忆有选择性，但可能漏召回并引入旧事实。当前保留有限前问窗口，新增确认记忆但不加滚动摘要或记忆向量库。冻结输入有版本、类型和身份标记，每次入模前再次排除已删、过期或改版的条目。

### 36. 失败反馈是否进入下一次决策

当前任务链路：Verifier.issues → state.issues → 路由决定有限修订 → Analyst 请求。旧实现只有 issue 的 claim_id 和原因，没有对应旧草稿。本轮补传 previous_draft，并明确它只能作为修订对象。

新增回归使用 CapturingProvider 实际捕获两次 Analyst 输入，验证首次没有旧草稿、第二次的错误 ID 能定位到原论点文字和对应原因；正常工作流完成。ModelCall 仍记录实际入模请求，能进一步核对传入的数据。

这证明本任务反馈到达下一次请求，不代表真实模型一定正确修复。范围确认后另加了跨任务记忆链路：候选 → 本人确认 → 身份/类型/快照过滤 → 新运行冻结 → memory_hints 进入 Planner/Analyst；捕获实际请求的模拟回归证明已确认偏好到达、未确认候选没有到达。其他任务的原始用户反馈仍不自动召回，也不影响之后所有问答。

### 37. 正式知识库的入库条件

当前发布条件是：编辑者/管理员明确上传 → 文件内容和哈希检查 → 解析/分块/Embedding 成功 → 索引 ready → 启用当前版本。它只证明资料技术上可查询；不代表制度由人工批准或内容真实。

模型答案、用户反馈、历史失败和外部工具响应目前均不自动进入资料索引。拒绝答案、拒绝保存偏好、拒绝外部资料是不同事件。可信系统证明可用于确认文件来源和版本，不能代替其业务权威性。

如果用户需要待审资料区，应新增候选版本、来源、审核人/时间与发布记录，批准绑定内容哈希，未批准内容不进当前快照。人工审核工作流超出现有范围，本轮仅列出边界，没有伪称已实现。

### 38. 持久化、清理及用户隔离

问答/模型/检索/反馈保存在业务数据库，非浏览器内存；登录会话也存数据库，过期时间与内容留存是两回事。私人运行按已认证用户过滤，同时检查当前知识库成员关系；知识库文档由成员共享，不是按上传者私有。

现已新增个人偏好与经验存储、查看、版本修改/重新确认、删除和本人过期清理接口。过期立即停止召回；清理是本人显式操作，没有全局定时作业。删除擦除当前记忆正文，不抹去已发送模型请求或历史 trace/config；账号退出不删除问答，文档软删除也不物理清理引用。

记忆沿用正文数据库管理身份、类型、版本和确认状态，经验还检查知识库成员和文档范围；修改后回到候选，不静默覆盖同名确认记忆。本轮验证跨用户访问、撤权、版本冲突、过期、删除和实际入模路径。不删除旧任务、会话或原问答证据。

### 39. 版本更新、删除和模型切换

正文/原文件是主存储，Chunk 是检索表示；Snapshot 固定文件、解析和索引，EvidenceSpan 指向原文字符范围。新文件版本成功后才启用，更新失败保留旧文件版本；历史答案不随正文更新而改写。

本轮分块规则升级有针对性回归：把索引标记为旧规则后，当前配置检索明确拒绝并提示重建；旧快照清单和原文引用仍可核对。没有覆盖旧向量、回写历史论点或自动付费重算。

已有 reindex 会把同一文件版本暂时改回 uploaded；它不具备“索引重建过程中旧索引持续服务”的保证，失败后需重试。它与“上传新文件版本失败保留旧版”是两种流程。历史答案可读，不代表过期快照能重新执行：新问答/追问/回放仍要求版本当前可用。

切换 Embedding 模型/地址/维度/revision 或分块规则需新索引和新快照。聊天模型变更由运行配置检查。经验仅匹配同一 manifest 哈希，新文档/索引范围下不再复用旧经验；没有摘要和记忆向量投影。记忆冻结清单保留当时的内容与版本，随后删除或修改只影响后续调用，不改写历史输入。

### 本轮实现说明

**具体问题：**任务入口没有并发积压限制；API 上传同步代码可能阻塞事件循环；Provider 固定请求时限、没有明确有限重试/熔断；Embedding 短暂失败会使检索整轮失败；失联任务可反复被新 attempt 执行。

**为什么放在这些位置：**容量必须在数据库创建任务/领取任务时由服务端强制，避免只限制前端或 Celery 本地队列；请求预算和网络重试位于 Provider 适配器，能统一约束聊天与向量接口；Embedding 故障降级位于检索融合边界，只有在关键词结果可独立解释时才返回，并在 Trace 明示能力收窄。

**数据流：**同步上传路由交给 FastAPI 工作线程读取文件 → 数据库容量行串行检查入队并提交版本 → Celery beat 定期投递、worker 按租约领取且受并发上限约束 → Workflow 把任务截止时间与 attempt/取消/权限检查传到 Provider 和解析循环 → Provider 对可判定的连接、429、服务端错误有限重试 → 检索遇到可重试 Embedding 失败时保存失败 ModelCall、关键词候选与 `retrieval_degraded` 事件 → Trace 显示调用失败及实际降级路径。

**代价和边界：**新增一张容量锁表及迁移；短事务锁会让入队/领取短暂串行。默认阈值是容量保护初值，未经过负载校准。worker 默认并发 1，任务领取的数据库上限默认 2；跨进程容量由数据库锁协调，但 Provider 熔断仅在单进程内。读超时不重试可能让任务失败但避免不明重复费用；关键词降级会降低语义召回。模型服务已处理但响应丢失时仍可能计费，数据库 attempt 不能撤销供应商副作用。

**面试表述：**“我把容量控制放在数据库任务边界，避免队列无限堆积；每次模型请求受总 run 截止时间限制，只对明确的连接失败、429 和服务端错误做有限重试，读超时不盲目重放。Embedding 瞬时失败时允许带标记的全文降级，Trace 保留失败和实际走过的路径。控制测试通过，但 Redis/PostgreSQL 并发和真实模型效果还没有联调。”

**可能追问：**为什么限流、重试和熔断不是一回事？答：队列上限控制尚未执行的工作量；重试处理可恢复的单次瞬时错误；熔断器在一段时间内连续失败后暂时拒绝新调用。三者分别保护积压、单请求和持续故障。

### 十三、拒绝反馈、知识发布与失败回归

#### 66. 用户拒绝时，应该问清什么？

**旧行为与问题：**`ReviewRecord` 仅存 answer_id、用户和自由文本，“不满意”无法区分措辞偏好和事实错误，也没有读取反馈的 API。

**已实施：**`schemas.ReviewCreate` 接收用户选择的 preference/factual_error/execution_failure/missing_scenario/requirement_change/unable_to_complete/unclear；原话保留空白，禁止全空白。`main.review` 在鉴权后先保存原话、分类、答案内容哈希和可选幂等键；`unclear` 返回具体澄清选项，绝不猜分类。新增本人反馈 GET，前端接入分类选择和已保存反馈回看。

**方案与取舍：**规则/模型自动分类可能把偏好误判成技术缺陷，且增加调用；用户选择加“原因待澄清”更符合本地最简版。分类来源明确为 user_selected/unclassified，不是已证明的根因。历史反馈不覆盖答案，也不直接进入检索知识。已验证原话、幂等冲突、空白拒绝、跨用户不可见以及无新增模型调用；浏览器端到端尚未验收。

**代码修复扩展：**拒绝补丁时除保留原话外，还记录用户选择的反馈类别、可能根因层和未确认事项。根因层只代表审核者的当前判断，不由模型自动归因；拒绝记录可以在任务详情重新读取。

#### 67. 拒绝经验怎样变成长期回归用例？

**当前与建议：**原话已持久化；没有实现自动生成测试、隔离双向复现、人工发布正式回归集的整条闭环。可选个人记忆中的“失败经验”也不等于已验证技术反例。本轮不把用户偏好转成技术断言，不自动执行生成代码。

**推荐流程：**原反馈 → 脱敏副本 → 人工明确目标行为与旧版本 → 候选用例及来源哈希 → 隔离运行 → 人工核查反例有效 → 带版本发布。修缺陷时旧版因目标缺陷失败、修复版通过；判断补丁破坏正常行为时基线通过、拒绝补丁失败。依赖缺失、语法错误、收集失败和无关断言不算有效反例。

**取舍与验证：**先由人工编写有行为断言的回归，比立即引入生成/执行/审核平台简单。失败候选保留原反馈、测试内容、运行环境、标准输出/错误和失败原因，不能发布为成功知识。本轮预算/未知 usage 的回归是人工编写的控制测试，不是已跑通自动反馈闭环。

#### 68. 怎么避免审核了 A，却发布了 B？

**现状（第四部分收尾时）：**知识库答案当时在确定性引用/语义核验后发布，每 run 仅一版；用户反馈绑定 answer_id 和答案完整序列化内容的 SHA-256。反馈记录“评价了哪一版”，不代表人工批准。答案发布审批随后在第一部分扩展中实现，当前门禁见[第一部分实施核对](第一部分_协作输入与工作流基础_实施核对.md)。可选代码修复/外部写模块有各自的补丁哈希或操作 digest，属于独立扩展。

**方案比较：**只绑定任务 ID 无法识别内容更改；绑定完整对象的版本/哈希并在提交前重算可拦截旧页。若将来做失败回归发布，批准对象至少覆盖原反馈、测试全文、验证命令/环境与报告；改其中任意一项使旧批准失效。并发修改以服务端版本比较处理，不能只禁用前端按钮。

**本部分当时的边界：**没有新增答案审批或回归集发布状态机；不能因反馈有哈希就声称整套人工审核已完成。答案审批后来另行实现；回归集发布状态机仍未实现。外部工具授权的 digest 检查由对应扩展测试，不以问答反馈测试替代。

代码修复审核另有 `verification_sha256`，覆盖基线、任务目标、选中文件、摘要、补丁哈希、固定测试命令、Docker 镜像 ID、测试文件清单、退出码和完整输出哈希；审核时重新校验。`CodeRepairReview.bundle_sha256` 绑定接受/拒绝记录，和 `artifact_sha256` 补丁哈希分开，避免把补丁版本误当成测试证明。

#### 69. 修复应该落在哪一层？

**本次归因：**无 usage 被当零是适配器与统计契约问题，因此在 Provider 标记未知、数据库保存预留、API 显示 null、评测汇总识别未知；HTTP 重试绕过累计预算落在 Provider 发送边界与 Workflow 预留；含糊反馈分类落在输入/持久化与前端选择，不加模型提示词猜根因。

**选择理由：**缺原始资料应补知识，已有资料未进入上下文应查检索/重排；工具误用查 Schema/适配器；权限落到后端；遗漏恢复/验收步骤查状态流。每层解决不同问题，不能靠一条“请准确回答”统一兜底。本次沿同一复现检查旧行为和新行为，代价为每次请求前后新增持久化及保守估算。

#### 70. 后续服务失败，会不会丢掉拒绝记录？

**已实施并验证：**反馈 API 在一个数据库事务保存后返回；处理反馈不调用聊天或向量服务，也不触发重排、发布和索引。因此后续模型故障不能撤销已提交反馈；重复请求同幂等键回同一记录，换内容返回 409。GET 可回看原话，跨用户和被撤权访问仍经原答案归属检查。

**未实现的部分：**没有反馈处理后台队列、向量化或自动补做。未来若加候选生成，先保存原反馈，再按稳定 feedback_id 分 pending/needs_human/validated/published/failed；正文落盘、索引可用、回归发布必须是不同状态。不能把当前“已保存”称作“已自动学习”。

代码修复拒绝采用先提交审核记录和 `cleanup_pending`，再回滚 worktree 的顺序。清理失败时保留原始理由并记 `cleanup_failed`，页面可单独重试清理；清理成功记 `restored`。这是为避免清理与数据库提交跨资源事务导致反馈丢失，不代表拒绝反馈已经变成回归用例。

### 十四、请求预算、并发与缓存

#### 71. 能否在发请求前控制 Token 和费用？

**已实施：**`governance.estimate_tokens` 使用 UTF-8 字节数加固定余量估算；Workflow 请求前锁 run、累计所有 attempt 的已知用量/未知预留、验证单次与总额度、按剩余额度缩小输出上限，先写 `ModelCall(status=started)` 和开始事件，事务成功才发送。Provider 另有聊天输入/Embedding 单条或至多 16 条批量输入护栏。

**重试：**Provider 在下一次 HTTP 发送前调用 `before_retry`；Workflow 保留前一次完整预留并标记未知，再为新尝试建账，最终 usage 只结算当前尝试。复核曾发现缩小重试输出额度后将未知预留从 7448 错记为 2552；行为回归已复现，现保留原预留，不因重试缩额减少先前潜在消耗。结构解析失败保留已收到 usage；无完整 usage、超时或进程崩溃记未知，不计为零。

**费用：**可选 `MAX_RUN_COST`，需模型当前价格、币种和价格来源；缺价格时拒绝启用该费用预算。成本按输入/输出每百万 Token 价格估算，未知调用保守保留预留；未配置价格时 cost=null。默认不开金额上限，不假造供应商价格。优先采用保守护栏，未引入供应商 tokenizer/账单查询；估算误差、HTTP 框架开销及供应商计费差异意味着不是精确硬账单上限。文档入库有单批输入护栏，但不属于 question run 总额度，尚无跨文档全局金额账本。

#### 72. 预算耗尽后，返回部分、降级还是请求继续？

**已实施：**时间、调用次数、Token、费用、单次输入与检索轮数分别保留 `budget_category`；发布仅保留已完成相应检查的论点，完整模式未被 Verifier 批准的草稿不能因额度不足直接发布。缺口使用对应中文标签；没可发布论点则 insufficient，不伪装 supported。

**边界：**关键词降级来自 Embedding 瞬时故障策略，不因预算不足绕过核心验收。钱和 Token 不随 checkpoint/attempt 重置；从首次 started 计算 wall-clock，恢复等待也计入，排队前等待不计。停止后仍执行持久化/心跳线程收尾，已经发送的远端请求不能撤回。没有“追加预算继续”按钮，也没有人工等待中续算语义；对外部操作不能把预算耗尽当成远端未执行。

#### 73. 追加预算怎样做到不重置历史、不重复加钱？

**现状：**不支持原 run 追加/续跑；已有的 replay 是新 run，有新清单和预算，会再次调用模型。本轮修复的是恢复不能清空已用预算，不能称为追加预算已实现。

**方案：**简单新建 run 最易解释但会重复检索/付费；真正续跑需要 BudgetGrant（run、发起用户、原因、各类增量、幂等键、创建时间）、初始清单不变、行锁内同时写额度追加与状态。稳定幂等键应将重复点击/响应丢失合并，同键不同内容返回冲突。累计可用额度=初始+grant−已耗/预留，不能覆盖初始值。

**续跑前提：**确认归属、当前角色、有效快照、明确恢复节点、旧 worker 停止和环境清理；存在未知外部结果先核对，不能直接重放写操作。初次实现与测试成本较高，目前没有实际任务要求追加，保留设计而未添加状态机。

#### 74. 并行、排队和领取任务怎样配合？

**已有：**第三部分 `capacity.py` 通过 `workload_gate` 串行准入/领取；默认待处理 40、每用户问题 3、有效租约并行任务 2、恢复 attempt 3。Celery prefetch=1；Windows worker 默认 solo，不预领大量任务。这里引用第三部分的控制测试，不将其成果重复计数。

**推荐：**多个 run 可由不同 worker 处理，内部 Planner→检索/重排→分析→核验有依赖，保持顺序。独立查询可并行，但当前检索还会共享证据去重、事务和预算，直接 gather 会扩大锁冲突及供应商突发量；先保留顺序，在真实 PostgreSQL/Redis 与模型配额压测后再定并发。新增请求预留是 run 行锁保护，不能只靠进程内计数。未知并发实际 QPS/P95 不填成绩。

#### 75. 哪些结果可以缓存，怎样失效？

**现状与判断：**没有新增业务缓存。已有文档内容哈希、索引版本与快照不是模型响应缓存；`get_settings` 的 lru_cache 只是配置读取。当前缺相同请求的真实复用频率与收益证据，先不增加缓存服务。

| 对象 | 将来可用的缓存键与失效依据 |
| --- | --- |
| Embedding | 文本内容哈希、Provider/模型/维度/revision、估算/输出契约版本；权限仍在取用时检查 |
| 检索 | 用户/库/权限身份、快照和索引版本、查询、路由/重排参数；撤权或当前版本变化必须重新鉴权 |
| 代码分析 | 可选代码任务的确切源码树/未提交内容、分析器与配置；不能只用路径或 commit |
| 模型输出 | 规范化完整输入、提示词/Schema、模型/参数、资料版本与用户/记忆权限；成本和新调用身份不能伪装历史 |
| 外部工具 | 只有明确只读且有业务 TTL/版本证明的结果；当前外部状态、批准、未知写结果不能据缓存认定 |

TTL 只作补充，不能代替内容/权限版本。实施后需测命中率、端到端收益与过期错误；仅写入缓存不能证明优化有效。

### 十五、配置冻结、Trace 与环境诊断

#### 76. 一次任务的完整配置能否查出？

**已实施：**创建 run 时保存原始问题身份、最多四条前问、快照哈希、模型/服务身份、生成与预算/重试参数、价格来源、角色提示词全文和 Schema、应用文件/锁文件哈希、主要已安装包版本、记忆上下文及总 manifest 哈希。trace 和 recording 可读取；执行前核对清单、模型服务、应用源码、锁文件、主要依赖与材料身份，变化则拒绝旧 run，不能静默切换。

**取舍：**使用显式允许字段，密钥只记环境变量引用、地址只记身份哈希；无凭据版本系统。此清单覆盖知识库问答，不冻结可选 MCP 运行时发现的全部工具权限，也不保存 Python/系统依赖镜像、源码归档或模型真实权重版本。授权/记忆删除仍由当前后端规则执行，不能拿冻结清单维持已撤销权限。严格代码身份检查会使更新后排队 run 失败，需重新创建问题；这是可见的限制。

#### 77. 记录回放与重新执行一样吗？

**已实施：**新增 `GET /api/question-runs/{id}/recording` 只读保存的 run、全部事件、trace，返回未完成调用 ID，不调用模型/工具，不补造缺失响应。历史旧记录可能没有开始事件或清单，明确给限制。原 `POST .../replay` 继续创建新运行，本次保留原 parent_run_id，使追问重新执行仍有前问；`replay_of` 创建时纳入冻结哈希和幂等内容比较，复用原请求 key 会返回冲突，不能把原 run 改成重跑。

**选择与边界：**读取记录适合定位当时的输入、证据选择和状态；新执行适合复测当前配置，可能再次付费且输出不同。界面原“重试”继续新执行，recording 先以 API 提供，不伪称有时间轴播放器。权限和当前可用版本仍约束新执行，历史只读不保证任意旧快照可重跑。HTTP 未完成、缺记录原样显示未知。

#### 78. 有 commit/哈希就能重建环境吗？

**不能。**当前目录没有 Git 元数据，不擅自 init；应用/锁文件 hash 只作识别，不能恢复丢失内容。已有 uv.lock 和 package-lock，Compose 仍是镜像标签，未固定/归档 digest；供应商模型为别名。没有自动环境重建，清单明确 `hashes_only_no_source_or_image_archive`。

**推荐：**应用源代码与未提交差异独立归档、保存可获取依赖包与镜像 digest、系统/Python 版本、数据库/对象存储备份和迁移基线，另做净环境重建演练。服务代码版本与可选待修复仓库 checkpoint 分开。代价为存储和演练维护；本轮没有借“可复现”扩大承诺。

#### 79. 完整 Trace 应记录到哪层？

**已实施/整合：**run/request_id → attempt → 节点事件 → ModelCall ID → Provider HTTP 尝试/重试 → 检索与来源 → 答案。调用发送前落 started/预留，成功或失败后保存响应摘要、usage 已知位/供应商 ID/耗时并结束；崩溃留下 started。HTTP 重试另有未知预留，节点耗时不与内部请求耗时简单相加。

**已有与未有：**第三部分提供 HTTP 尝试/降级事件、规则脱敏；可选 MCP/外部操作有独立回执/审计。主链不是 ReAct 任意工具循环，没有不可见模型思维输出，也没有集中监控告警。调用前写库失败会阻止对应请求，已加入故障注入断言；远端完成但本地收尾失败仍可能是未知，不能由审计声明回滚。规则脱敏无法识别所有未知秘密，业务摘录仍受本人/库权限保护。

#### 80. 端口启动失败与业务失败怎样区分？

**本轮未遇到新的 bind 错误，不推测端口原因。**实际 Docker 错误是命名管道 `dockerDesktopLinuxEngine` 不存在，是 Engine 连接失败，不能说成 55432/56379 占用。当前 API/前端默认仍为 8000/5174，数据库/Redis 映射 55432/56379。

**诊断顺序：**记录实际 WinError/OSError、绑定地址及进程是否退出 → `Get-NetTCPConnection -State Listen` 查对应 PID → 用 `netsh interface ipv4 show excludedportrange protocol=tcp` 只读核对系统保留范围 → 检查 backend 启动、Vite proxy 与请求 URL 一致。未监听可能是未启动而非占用；API 已启动后模型 HTTP 超时属于业务依赖故障。当前无证据需要换端口或修改防火墙/权限，因此未操作系统配置。

### 十六、可验证评测、真实验收与版本治理

#### 81. 正式评测要求 Markdown

**已编写：**`evaluation/评测要求.md` 定义开发/冻结集、正常/边界/恶意/故障覆盖、分层归因、人工评分、对照、分母、P95 与产物。控制集要求已定义不变量全通过、安全硬失败为零；实际质量/费用/延迟阈值需在正式实验前填写冻结，目前没有被确认的效果目标。

**已改工具：**运行器接登录（不回显密码或环境会话令牌）、本机禁用代理环境继承；轮询超时/失败仍尝试取消并抓 trace，取消失败明确 unknown。汇总使用 manifest 全题分母，缺文件计失败、未知/重复题号报错、非终态不算完成；已知 Token 小计与未知次数分开，增加含失败尝试的 P50/P95/max/观测数。合并的价格汇总要求全部有估价及价格来源、同一币种；未知或混币种不相加。

另有探索性问题级 Top-5 报告：人工为冻结快照填写 `relevant_chunk_ids` 后，只核算首 attempt 第一轮的主查询，避免子查询和重试扩大分母；这不是 query-specific gold 或 Recall@5。费用只在每个 run 的 usage 与价格都可估算且币种一致时汇总，否则为 null。

**未取得：**真实团队材料、独立人工冻结集、检索/语义评分器和正式成绩。规范、模拟 HTTP 测试和真实完整评测是三种不同证据。

#### 82. Top-5、修复成功数、回归通过率怎样算？

**定义与实现：**规范仍区分 Hit@5 与 Recall@5。汇总器提供探索性的首查询 Hit@5：仅取每道有 `relevant_chunk_ids` 标签题的首 attempt、首轮、第一条请求 top 5；分母固定为全部有标签题，缺失计未命中并单列。不同子问题与补检不会被合成大于 5 的候选集，也不通过增加查询稀释失败。标签仍是问题级，不等于完整子查询检索评测或 Recall@5；正式实验前仍需独立人审和口径冻结。

**适用边界：**本项目主流程回答问题，不做 30 个代码修复 benchmark；可选代码任务测试通过也不等于独立隐藏验收的修复成功。回归通过率须列测试用例总数、失败/超时/跳过，或明确是候选产物分母。问答三模式共享混合检索，不能冒充 RAG 开关修复对照或纯检索三路实验。

**结果：**82%、16/30→22/30、96% 在原清单是示例；无证据则不能采纳。本轮新增确定性测试数和 P95 汇总能力不产生任何这些数字。

#### 83. Docker/worktree 真实端到端验收

**预检演进与当前结果：**早期 `docker version --format '{{json .}}'` 曾返回 `Server=null`、Linux Engine 命名管道不可连接；该次真实容器验收 blocked。收尾时重新执行同一命令，Client/Server 均为 29.7.2，Engine 已恢复；当前全量包含独立样例仓库的真实 Git worktree 与 Docker 控制测试。模型补丁响应是固定的，不是实际模型修复效果。项目根目录仍不是 Git 仓库，不初始化或建立无关 worktree。

**真实复验：**`tmp/part4-validation/verify_docker_isolation.py` 使用独立合成仓库和固定补丁，实际基线因 `1 != 2` 失败（exit 1），补丁后通过（exit 0）。记录 Engine、确切 image ID、运行中 inspect：只读根/工作区、禁网、非 root、512 MiB/1 CPU/64 PID；容器内断言 `.git`、`.env`、模型密钥不可见，写盘和外网连接失败，源仓库内容哈希不变，测试输出回到宿主。将测试 deadline 控制为 1 秒触发真实超时（exit 124），无遗留该任务容器，工作副本恢复到基线；完整证据见 `docker-isolation-latest.json` 指向的 result.json。

**暴露并修复的缺陷：**首轮真实超时在 Windows 上产生 stdout 字符串、stderr=None，旧拼接字节方式抛 TypeError；实际失败输出保留 `docker-isolation-before.log`，修复为各部分先解码，再跑同一场景通过。新增两项受控回归覆盖字符串/字节输出。样例固定补丁不代表真实模型修复质量；没有执行 30 个任务的 RAG 开关实验，也未验收 PostgreSQL/Redis 整栈。资源参数被 inspect 确认，不等于对任意恶意代码的绝对隔离证明。

#### 84. 模型、提示词、知识、工具变更如何上线/回退？

**已编写：**`evaluation/版本发布与回退.md` 给出版本组合、同题配对回归、关键场景门槛、限定账号验证、停止条件和数据/索引兼容回退步骤。run 清单可识别组合，尚无发布台账 API、镜像归档或真实灰度。

### 逐题讨论

#### 86. 演示界面连接真实工作流

Vue 已通过 FastAPI 创建真实快照和问题任务，使用 SSE 读取持久事件，页面刷新后按运行 ID 重新读取任务；这不是固定补丁或假进度。该题中的补丁接受/拒绝流程属于代码修复 Agent，当前有 `CodeRepairTask` / `CodeRepairReview` 数据模型和迁移，但没有路由、工作流或前端入口。结论：知识库问答链路已接通；不为补丁审批扩展产品。

#### 87. 模型调用前的业务范围门禁

当前业务本身是知识库问答，登录、知识库成员和固定工作流限制了可访问数据及动作；没有一个通用“软件开发范围”分类器。添加代码生成/审查等门禁会改变产品目标，且可能误拒对文档的正常提问。结论：不增加代码 Agent 范围门禁；若以后限定知识主题，应先定义明确的知识库级范围和拒绝例子，再放在 Planner/Embedding 前验证。

#### 88. 歧义澄清

Planner 的结构化结果支持 `needs_clarification` 和具体 `clarification`；工作流将澄清结果持久化为 `needs_clarification` 答案，不进入检索。用户补充后创建新 run，不是在原 LangGraph 节点暂停后续跑。Schema/Provider 错误和权限错误走失败/拒绝路径，不应伪装成业务澄清。结论：当前问答所需的“不猜并询问”已有实现；通用可恢复暂停状态不属于现有工作流。

#### 89. 多工具冲突与整批预检

当前模型不提出可执行工具批次；服务端固定提供快照范围内的搜索和原文读取，均为只读。没有多个外部写操作、冲突组或需要资源锁的目标。结论：不新增批次冲突引擎；如以后接入写工具，应在执行前一次校验整批权限、参数、冲突声明和资源锁，且任一失败时零操作。

#### 90. Schema 纠错与服务端拒绝

API 和模型输出使用 Pydantic Schema，`ScopedTools`、证据范围、用户身份及知识库角色还由服务端单独校验。模型返回格式无效时当前按技术失败处理，不进行无限重生成；格式合法也不代表有权限或符合业务意图。结论：对现有固定检索路径，区分结构校验和授权已足够；动态工具参数纠错需等工具接入后再设计，并限制轮次。

#### 91. 结构化错误与诊断

已有 Domain/Provider 错误码、用户可见错误、run ID/request ID、持久事件、Trace、模型调用与 Provider 尝试记录，并在日志/Trace 写入前遮蔽已知凭据。数据库异常向用户返回通用提示；worker 内部错误只记录异常类型，Trace 本身写失败和集中告警没有完整机制。结论：当前主要问答路径可诊断，但不能称为浏览器、MCP、Docker、外部操作的全层故障系统；后几层没有对应运行链路。

#### 92. 超时、重试与未知结果

Provider 对明确的连接失败和部分 HTTP 429/5xx 做有限重试，尊重 `Retry-After` 和 run 截止时间，并配置进程内熔断；读超时不自动重放，因为远端可能已完成。Embedding 瞬时故障可标记降级到全文检索。当前没有数据库外部写工具、代码测试副作用或 MCP 写入回执。结论：已实现的模型请求重试边界适合只读问答；写操作幂等/结果核对须等该类工具成为明确需求。

#### 93. 用户、会话与业务权限

账号使用 scrypt 密码哈希；会话令牌只存哈希，浏览器 Cookie 为 HttpOnly/SameSite=Strict；管理员创建成员，知识库级角色决定读写权限，后端从已认证用户身份推导数据访问。没有公开注册、登录限流/锁定或独立 CSRF token；当前只监听本机并未宣称公网安全。结论：与当前本机团队范围相符；若部署到公网，需先定义威胁模型，再加限流、CSRF、会话轮换和部署边界测试。

#### 94. 对话摘要与长期记忆

Planner 最多接收同一快照下的近期父问题，用于代词指代；这只是问答上下文，不是跨会话个人记忆。`MemoryEntry` / `MemoryEvent` 有表结构和迁移，但没有可用 API、提取流程、用户确认界面或问答读取路径。结论：不把近期上下文说成长期记忆；个人偏好与跨任务经验仍是新增产品功能，未经确认不接通。

#### 95. 旧数据迁给哪个账号

本地管理员 bootstrap 使用稳定 ID `local-user`，并在创建该账号时为其所有的旧知识库补管理员 Membership；知识库创建者本身也由 owner ID 获得管理员角色。随机高熵初始口令写到本机 `data/admin-login.txt`，不是写入源码或 Trace。若历史库出现其他 owner ID 或无归属记录，不能自动转给当前登录者，需先盘点记录数量、归属和备份。结论：标准旧本地数据已有确定迁移路径，未知历史数据需单独审计。

#### 96. run_id、attempt 与 revision

`run_id` 标识逻辑问答任务；`attempt` 才是一次 worker 执行的 fencing 值，写入/发布都检查当前 attempt。LangGraph `thread_id` 由 `run_id:attempt` 组成。答案 `revision` 是答案版本号，目前每个 run 只发布 revision 1；修订通过新 run 创建，不是 `QuestionRun.state` 的 CAS 状态 revision。结论：旧 worker 防护由 attempt + 行锁完成；不要误称答案 revision 能防 JSON state 的过期覆盖。

#### 97. 恢复过程中断

租约过期会增加 attempt 并从初始状态重跑；检查点按 `run_id:attempt` 隔离。当前工作流没有隔离的源码工作区、恢复提交阶段或两阶段回滚。重跑可重新调用模型并再次计费，旧 attempt 不能发布。结论：代码 Agent 的 checkpoint A/B 文件恢复方案不适用于只读问答；保留当前从头重试边界并把重复费用作为限制。

#### 98. 只读诊断 Agent

Planner、Retriever/Reranker、Analyst、Verifier 是问答图中的固定职责节点；证据缺口会返回部分答案、材料不足或澄清。没有第二个诊断 Agent 查询 Docker、MCP 或操作回执的路径。结论：目前增加一个诊断 Agent 只会增加模型调用和新的不确定性；如将来需要，可让其整理已有 Trace 并建议只读查询，但状态和权限仍由服务端决定。

#### 99. 回滚边界

本产品的写入包括本地文档文件及版本、知识库/问答数据库状态和任务事件；移出文档是软删除，历史引用仍保留。模型/Embedding 请求的费用不能由本地恢复撤销。没有任务源码工作区、远程 MCP、邮件或订单写入。结论：数据库事务可回滚未提交更改，checkpoint 只恢复工作流状态，不等同业务/文件/第三方回滚；物理删除和外部补偿均不在本轮范围。

#### 100. 预算类别与展示

配置及运行路径已区分总 Token 估算、单次输入 Token、模型调用数、检索轮数、修订轮数和单次 attempt 运行秒数；模型费用只在用户提供价格信息时估算，unknown usage 保持未知。Trace 提供 `budget_category` 和 accounting；主问答界面目前只显示模型调用、检索轮数和时长，没有展示全部用量/价格状态。结论：后端预算基础已存在；若要增加用户侧费用明细，应明确只显示估算并显示 unknown，不能称为账单。

#### 101. usage 缺失及计费证据

当前模型调用是非流式 HTTP 请求。发送前记录 Token 预留；响应有 usage 时保存 Token 数、供应商 request ID 和状态，没有最终 usage 时保留 `usage_known=false`，按预留量限制总预算。若进程在供应商完成后、数据库写入前崩溃，可能只剩 started 记录而没有供应商 ID；本地无法精确对账，也不会从文本长度伪造用量。结论：题目中的流式最终 usage 情况当前不适用，但 crash window 和 unknown 语义仍存在。

#### 102. 运行预算与 checkpoint 清理

`max_run_seconds` 在每个 Workflow attempt 启动时计时，排队时间和两次 attempt 间等待时间不计入；模型调用、Token 预留及调用次数从 ModelCall 跨 attempt 汇总。租约恢复会启动新 attempt，因此累计 wall-clock 可能超过单个 `max_run_seconds`。本系统没有容器/源码回滚清理；worker 仅在 `finally` 停止心跳线程，且安全收尾不应被模型预算跳过。结论：如要把秒数改成整个 run 的累计上限，需先确定排队时间是否计入、恢复间隔如何计时及截止后如何落失败状态；本轮保持既有语义并记录此差异。

#### 103. MCP 写入与人工审批

有 `MCPInvocation`、`ExternalOperation` 表和 Schema，但当前没有 MCP 客户端、发现/调用 API、外部服务配置、审批 UI 或操作执行器。MCP 仅是协议，表存在不能证明真实写入已实现。结论：不声称有 MCP，也不接入未指定服务；真实写入需明确端点、工具白名单、目标资源、绑定参数、幂等键、结果未知处理和审批人。

#### 104. “不影响主业务”的保护目标

本系统没有执行用户代码或访问第三方写服务；它有登录、知识库角色、文件上限、本机监听和快照范围约束，但会写本地文档/数据库并调用配置的模型服务。模型服务可能产生费用，也会接收所选上下文；本机进程故障仍可影响本项目的数据和可用性。结论：可承诺的是具体访问/资源边界和已测试不变量，不能保证任何情况下零影响；无需为不存在的代码执行器引入容器沙箱。

#### 105. 风险验收

现有确定性测试覆盖澄清不触发检索、越权拒绝、引用校验、预算终止、Provider 重试/超时/熔断、attempt fencing、SSE 续读和容量上限。没有工具批次、MCP 写入、容器测试或未知外部回执，因此不能报告这些场景的硬失败率。结论：当前可用测试验证问答服务端不变量；真实模型效果需独立人审题集，服务依赖和浏览器端到端仍按 TODO 验收。
