## 为什么把证据检查提前

例如用户同时问“Mei 的角色、审批人和月薪”，角色表只有前两项。过去先生成候选答案，再依赖 Verifier 删掉推测；现在先确认哪些子问题有依据，让缺失部分直接进入缺口，减少不必要的答案生成。

`backend/app/agents/workflow.py` 新增 `evidence_gate` 节点；`schemas.py` 限定输出格式，`prompts.py` 定义检查要求，`quality_gate.py` 验证子问题和证据 ID 的绑定。它位于最终来源汇集之后，能同时检查知识库片段及已授权只读工具的观察；来源内容仍是待分析数据，其中的指令不能授权操作。

每个计划子问题必须恰好有一条判定：

| 判定 | 后续行为 |
| --- | --- |
| ready | 可交给 Analyst 回答；仍需 Verifier 与发布前校验 |
| partial | 只回答有证据的部分，保留缺口 |
| missing / uncertain | 该子问题只保留缺口，不允许凭常识补答案 |

ready/partial 必须引用本次提供的真实证据 ID；未知、重复、遗漏子问题或重复证据会被拒绝。理由不能全是空白。缺口最多提出两条补检表达，整轮最多执行三条去重后的新查询；同一任务的既有检索轮数、时间、调用和 Token 预算继续约束它。全部子问题都不可回答且不能继续补检时，直接保存证据不足结果，跳过 Analyst/Verifier；完全没有来源时连 EvidenceGate 模型调用也跳过。

Analyst 若忽略限制、对 missing/uncertain 子问题生成论点，确定性检查仍会阻止该论点发布。预算在生成后、核验前耗尽时，也不能把未核验候选当作通过结果。部分判定的具体语义仍依赖模型与既有人审，程序只校验绑定和明确禁答状态，不声称证明所有内容正确。

代价是通常每轮多一次 EvidenceGate 调用。默认 `MAX_MODEL_CALLS=8` 保持不变，因此留给补检或修订的调用可能变少；不会为了新机制自动增加开销。`EVIDENCE_GATE_ENABLED` 进入每次运行的冻结配置，可在隔离评测中关闭；基础 RAG 与 without_verifier 组不启用此节点。实际运行中的问题继续使用自身冻结设置。

进度只显示固定的“检查证据”阶段和计数，检查理由、来源正文和候选答案不进入 SSE 公共进度。前端按该运行的配置隐藏关闭的阶段；正文仍在检查及既有人审权限满足后显示。

## 固定输入怎样比较

`evaluation/quality_suite.json` 绑定六份虚构文档的清单 SHA-256，包含原 15 道来源定位题、两道无答案题和一道部分可答题。原有保留对照题已经被开发过程查看，不能再称独立盲测。所有题保持 `human_reviewed=false`；缺失字段的预期也需要独立人工核对。

`evaluation/quality_profiles.py` 预先定义以下四组，不增加产品 API 的 mode：

| 组名 | 执行模式 | 生成前门控 | Verifier |
| --- | --- | --- | --- |
| baseline_rag | baseline_rag | 关闭 | 关闭 |
| without_verifier | without_verifier | 关闭 | 关闭 |
| without_evidence_gate | full_agent | 关闭 | 开启 |
| full_agent | full_agent | 开启 | 开启 |

baseline_rag 同时省略规划模型和模型重排，因此不能仅用它与完整组的差异归因于 Verifier。应分别用 without_verifier 对 without_evidence_gate、without_evidence_gate 对 full_agent 观察单项变化。四组固定为一次检索、不修订、最多六次聊天调用、240 秒和 150000 Token 预算；工作流 MCP/外部写操作关闭。答案人审仅在独立临时评测运行中关闭，语义评分仍必须另做人工审核。

`scripts/benchmarks/benchmark_quality.py` 是可选的隔离执行入口，默认三题两组，完整 18 题四组需 `--full-suite`；会调用实际模型并需要可用 PostgreSQL/Milvus，**本次没有运行**。脚本交错运行同一道题的各组，保存快照、冻结配置、逐题答案、轨迹、耗时及未知用量。已有 API 评测器遇到 review_pending/rejected 时立即记录受人审阻挡，避免一直等待到超时；不会自动批准答案。

`evaluation/review.py`、`report.py` 读取 manifest 中的组名，保留缺失/失败题分母，拒绝重复或不安全目录名。人工模板绑定 manifest 和逐题文件 SHA，未经完整独立人审，语义支持率和覆盖率保持 null，不能把模型核验通过率当作答案正确率。

## 重排和路由实验怎样隔离

`backend/app/knowledge/retrieval.py:retrieve_rankings` 抽出原有、受快照约束的两路召回供对照使用；正常 `hybrid_search` 继续等权 RRF 与原来的精确重复折叠，重排继续原聊天模型路径。

`evaluation/retrieval_profiles.py` 的五组规则在观察成绩前写定：关键词、向量、等权 RRF、关键词 0.7/向量 0.3，以及按问题文本选择权重。代码标识符优先关键词 0.8/0.2，比较问题 0.5/0.5，其余 0.3/0.7。它是显式规则实验，不是已经训练或部署的语义路由器。

`scripts/benchmarks/benchmark_retrieval.py` 准备相同的 RRF 前 12 个候选，分别交给当前聊天重排与本地 `BAAI/bge-reranker-v2-m3`，统计完整原文范围 Recall@1/5、Hit@5、MRR@5、上下文及耗时。候选池缺失的证据无法被任一重排器找回；聊天模型可以过滤候选，本地模型按分数取前五，分数不能直接互当阈值。路由比较复用两路召回，不能从该实验宣称某条路由的端到端延迟。

本地模型固定修订 `953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e`，六个推理文件合计约 **2.293 GB**。`scripts/models/download_reranker.py` 按发布 SHA-256/Git blob 校验文件；已完成下载校验。独立环境在 `tmp/rag-reranker-env`，模型在 `tmp/rag-models/bge-reranker-v2-m3`，主项目依赖未加入 torch。独立依赖见 `evaluation/requirements-reranker.txt`。CPU 推理脚本使用 batch=2、最大 1024 Token，记录截断对数及模型加载耗时，尚未运行验证，不能称已完成推理验收。

2026-11-14 轻量运行前检查：本机总内存约 15.7 GB；先后观察到可用内存约 2.6 GB 与 1.0 GB。模型权重文件为 2.271 GB（十进制字节换算约值），独立环境为 torch 2.8.0 CPU、transformers 4.57.6，未安装 accelerate。考虑权重加载期间临时对象和推理工作区，未启动 CPU 推理，避免内存压力；这不代表模型加载失败，也没有产生质量对照结果。固定检索材料仍是 15 道虚构且未独立人审题，不能作为业务质量结论。
