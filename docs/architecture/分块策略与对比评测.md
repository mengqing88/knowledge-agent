# 分块策略与对比评测

更新日期：2026-11-12。用户明确要求直接修改项目并做分块对比评测。

## 为什么修改

旧规则按原文字符累计到约 3200，原文块先按 2200 字符硬切，只在末片不足 800 字符时重叠。长句可能在中间截断，overlap 不固定；JSON 的数值虽然有字段路径定位，路径却不在向量化正文中。已有 3 篇短教学 PDF 无法区分 800/3200 两种长度，不能据此认定参数最优。

新逻辑在来源解析之后、向量化之前运行，继续输出 `text + source_ranges`。LlamaIndex 不再二次切分，LangGraph 的检索、原文核验和人审继续使用同一引用契约。

## 当前策略

| 策略 | 行为与代价 |
| --- | --- |
| legacy | 保留旧字符规则，用于历史对照；token 长度参数不控制它 |
| fixed | 按参考 token 长度形成滑动窗口；必要时按 Unicode 字符切开，能保留受控重叠 |
| paragraph | 原文块/表格行独立；超长块内部使用有重叠的窗口，不跨独立段落机械复制 |
| structure | 优先沿句号、问号等句子边界组合；过长句子才按长度切分，跨页或章节时结束 |
| semantic | 为相邻句片生成向量，余弦低于阈值时断开；该断点不复制前一主题，长度溢出时仍有重叠。额外模型调用、时延和 token 消耗需一起评估 |

本轮最终代码默认值为 `fixed / 512 / 64`，重叠最多约 12.5%，保留页/章节边界。最初的 `structure / 512 / 64` 是实验候选，实测出现退化，因此没有直接沿用。当前默认值依据控制集开发题选择，不代表所有业务最优。结构切分会优先容纳完整新句，因此实际重叠可以小于上限；跨页/章节/语义主题不强行重叠。当前位置标签也计入长度上限。

长度使用显式的 `cl100k_base` 参考 tokenizer；它不是 Qwen 服务的实际计费 tokenizer。分割点始终落在原文 Unicode 字符边界，不把半个汉字/emoji 解码成替代字符。原文范围仍引用未经清洗的 SourceBlock，合并相邻句子的连续范围，避免每句产生一条引用。重复页眉页脚过滤沿用原边界。

非默认章节/字段路径以一个有长度上限的位置标签加入检索正文，便于找到 `service.timeout_seconds = 45`。该标签是上下文，不伪装为原文证据；引用依然只使用原文范围。表格行的解析文本已经带列名，继续保留工作表与行位置。

配置示例：

```dotenv
CHUNK_STRATEGY=fixed
CHUNK_SIZE_TOKENS=512
CHUNK_OVERLAP_TOKENS=64
CHUNK_SEMANTIC_THRESHOLD=0.55
CHUNK_SEMANTIC_MAX_UNITS=128
```

约束：长度 32–4096，overlap 必须小于长度，语义阈值 0–1。语义策略另有限制每份文档的句片数量，默认 128，超过时在任何边界向量请求之前拒绝；长文实验显式设为 512，并仍受总 token、文本数和时限限制。实际 `.env` 未修改。新启动进程在未覆盖上述字段时使用默认候选；已有进程是否加载配置需另行确认。

## 版本与重建

策略、长度、重叠、语义阈值/句片上限、参考 tokenizer 和算法版本进入 `index_config` 指纹；执行清单也冻结分块字段。变更配置后，已有索引不会被静默当作新配置使用。对已有版本调用 `POST /api/paper-versions/{id}/reindex`，成功后创建新快照；保留旧 Chunk 和历史快照，旧答案仍可追溯。重建会重新调用 Embedding，不是只修改 collection 的参数。

这次对新默认值的选择不自动重建生产文件，不重启用户已有应用进程。Milvus/PostgreSQL 分工与权限范围检查继续保留。

## 对比实验

语料为 `fixtures/chunking/` 的 6 份明确虚构的文档：4 份长 Markdown 手册、1 份 CSV、1 份 JSON。长段落超过最大候选窗口。15 道问题含 9 道开发题、6 道保留对照题，包含跨文档双证据问题；标签唯一定位到原文块/字符范围。保留对照题不是独立盲测，作者可见题目与结果。语料和清单按 SHA-256 校验，没有人工审定的正式业务 gold。

比较 11 组：旧策略；固定 256/0、512/0、512/64、1024/128；段落 512/0；结构 256/32、512/0、512/64、1024/128；语义 512/64，阈值 0.55。

调用配置的真实 `Qwen/Qwen3-VL-Embedding-8B`，走真实 PostgreSQL 全文/RRF 与 Milvus/LlamaIndex。每组使用同样的问题和检索设置，单个查询预先嵌入并复用；不同策略的相同文本也可复用向量。临时数据库和随机前缀 collection 会清理，不写正式业务数据。

主要指标：

- **原文证据 Recall@1/5**：每题标注片段中，完整包含在某个 top K chunk 的片段比例，再逐题宏平均。分母是固定原文片段，与每组 chunk 数量无关。仅覆盖半句不算命中，同一原句被 overlap 复制多次不重复加分。这些标签只穷尽人为编写事实的证据，不等于全部业务相关片段。
- **Hit@5 / MRR@5**：前五是否找到任一标注片段，及首个命中的倒数排名。
- **成本与长度**：chunk 数、全部 chunk 的参考 token、实际源范围重复比例、top5 上下文 token、额外语义切分调用。共享缓存降低实验支付次数，但每组的全部索引文本量仍单独报告。
- **时间与失败**：建索引时间、缓存查询向量后的检索 P95；失败题保留在分母并计零。不把该 P95 当作问答端到端时延。建索引时间受跨策略缓存及执行顺序影响，只记录本次实验耗时，不用来宣称未缓存的生产入库更快。

脚本最多发送 600000 个参考 token、3000 个唯一文本，1800 秒总时限，无聊天/Reranker 调用；关闭供应商自动重试，保留未知 usage，不据此编造费用。缓存按服务/模型/修订/维度及文本身份区分；只保存在 `tmp/chunking-embedding-cache/`。

```powershell
.venv\Scripts\python.exe -X utf8 fixtures\make_chunk_samples.py
.venv\Scripts\python.exe -X utf8 scripts\benchmarks\benchmark_chunking.py
.venv\Scripts\python.exe -X utf8 -m pytest backend/tests/test_chunking.py backend/tests/test_chunking_benchmark.py backend/tests/test_llama_rag.py -q --tb=short
```

逐题排名、来源范围、用量和代码哈希记录在 `docs/records/benchmarks/chunking-benchmark.json`。正式业务质量仍需真实文档、独立人工标注、足够保留题，以及答案/引用支持检查；脚本不会根据这套合成分数自动修改生产参数。

开发集候选选择顺序：先比较原文证据 Recall@5；相同时优先不需要额外边界 Embedding 的策略，再比较 MRR@5 和上下文用量。保留对照题单独报告，不用它选择参数。本轮人工选定的代码默认值与理由会记录在最终结果中，脚本本身不改 `.env` 或生产文档。

若实验被中断，先保存已有 JSON，再用 `--resume-from <已有报告>` 续跑。只有语料哈希、模型、核心代码和策略配置一致、题目完整且无失败的结果才能复用；原始报告哈希、代码身份和用量记录会随新报告保留。续跑的 `embedding` 统计只覆盖本次网络请求，前一轮请求在 `resumed_from.source_embedding` 中，不把缓存命中当成新的支付用量。

## 实机发现的批次限制

初次预嵌入 15 道问题时，网关返回的索引为 `0..7, 0..6`，触发项目严格的响应索引校验。随后 2 条输入检查得到 2 个有效 4096 维向量。已将 LlamaIndex 桥接和评测网络请求上限改为每批 8 条，不放松供应商返回索引、维度及数值检查。较小 chunk 增加批次数后，这项兼容性修正也适用于实际入库。

第一次失败及中途稳定实现时的实验记录分别保存为 `chunking-benchmark-attempt1.json`、`chunking-benchmark-interrupted.json`。中途实验的临时资源已按其唯一前缀清理；不把未完成结果算入最终分数。未知用量不能直接按重试请求推定。

代码默认选择 **fixed / 512 / 64**：开发集 Recall@5 为 1.000，MRR@5 为 0.926；同样开发召回全命中的 fixed 1024/128 和 structure 512/0，其 MRR 分别为 0.889、0.750。它不增加语义边界调用，平均上下文也比 1024/128 少约一半。6 道保留对照题的 Recall@5 为 0.833，单独保留，不包装为独立正式验收。

与旧规则相比，整体证据 Recall@5 从 0.900 到 0.933，平均上下文从 9564 到 2425 参考 token，减少约 74.6%；向量条数从 18 增至 61，索引文本 token 从 23348 增至 27235，约增加 16.6%。这是合成控制集的证据召回及上下文取舍，不能写成真实业务准确率提升或账单节省。

fixed 1024/128 的整体 Recall@5 更高（0.967），但平均上下文为 4896；并非所有指标都由默认候选取胜。structure 512/64 的整体召回降至 0.633，说明不能把“结构分句加 overlap”先验当成最优。

当前 semantic 512/64、阈值 0.55 生成 416 个 chunk，整体 Recall@5 为 0.833；除 28201 个索引参考 token 外，还请求了 23344 个边界参考 token。单一阈值的相邻句余弦方法在这套语料中过度切分；这一结果不代表所有语义切分算法或阈值都更差。

常规十组完成后，语义组因每文档 128 句片上限在请求前失败。保留原报告 `chunking-benchmark-before-semantic.json`，将该实验上限显式设为 512，校验语料/核心代码/策略身份后复用十组完整结果，补跑语义组。最终报告保留前一轮报告哈希及调用记录；默认值选择仅修改配置默认策略，不改变已评测的显式算法/参数，并另存选择后的代码哈希。

所有本轮临时数据库与 chunk 前缀 collections 均已核验清理。选择前源码与 runner 快照保存在 `tmp/chunking-validation/`、`tmp/chunking-benchmark-before-resume.py`；既有应用进程未由本轮重启，旧文档需要按新配置重新索引后再创建快照。

## 面试表述

“我把分块做成固定窗口、段落、结构分句和语义几种策略，以 token 上限兜底，同时保留原文字符范围。用同一组问题和固定原文证据比较召回、上下文用量及索引开销，overlap 也作为实验参数。参数进入索引版本，调整后重建索引和快照，不能让旧向量冒充新策略。”

可能追问：为什么语义切分不直接默认开启？它要额外计算句向量，阈值依赖模型与语料；需要证明增加的成本带来可复现收益。
