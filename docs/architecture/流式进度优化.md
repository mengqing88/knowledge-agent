# 流式进度优化：检查完成后显示正文

2026-11-12 用户明确选择：“检查完成后才显示正文，等待时显示处理进度”。本轮实现按这一约定执行，沿用现有暖白、青绿、三栏工作台及答案发布审核权限。

## 原来的问题及这次的行为

原进度条使用 `12 + 事件数 × 4` 计算宽度。同一个模型调用可以产生多条事件，所以事件多不能说明答案接近完成；前端还会在每条 SSE 推送后查询完整任务及事件，并在健康连接期间每 1.6 秒重复轮询。首次断线后只剩轮询，不能恢复 SSE。

现在直接显示规划、检索、证据筛选、生成、核验、发布前复核的实际阶段，以及已等待时长、当前 attempt 的检索轮次、修订次数、已完成查询数和候选/证据数量。补检和修订会回到相应阶段，不使用估算百分比。baseline 模式不显示语义重排或 Verifier，关闭核验的消融模式也不显示 Verifier；发布前的确定性引用检查照常执行。

正文由原有 run/answer 接口在检查结束后返回。需要人审时，管理员/编辑者仍按原权限查看待审内容；普通阅读者等待审核通过。界面没有接收或逐字回放未核验草稿。

## 为什么在这些位置改

| 位置 | 改动及理由 |
| --- | --- |
| `backend/app/agents/workflow.py` | 节点开始前提交 `node_started`；每个实际检索查询结束后提交计数。原来只有节点完成事件，慢模型调用期间无法知道当前阶段。开始与发布都检查 attempt、取消状态和材料权限，已取消或过期执行不能新增开始事件或发布答案。原有来源、检索排序、核验和预算判断继续使用。 |
| `backend/app/agents/progress.py` | 把持久化审计事件投影成公开进度：只允许计数、已知阶段/模型角色及固定文案。计划、候选论点、缺口、核验意见和原文不进入进度流。过滤必须在后端做，否则只在界面隐藏仍可从网络响应读到。详细审计数据继续保存在数据库，按原 trace/recording 权限读取。 |
| `backend/app/api/main.py` | SSE 保留顺序号和 `Last-Event-ID` 恢复；立即发送连接注释，空闲时每 15 秒发送具名心跳。异步生成器每次查询使用短会话和线程池，查询后以 350 ms 间隔等待，断开时结束；不为一个长连接一直占用同步生成器的等待线程。满 200 条时继续排空，终态最后一页发送完才结束。 |
| `frontend/src/features/runs/runStream.ts` | 健康连接直接接收事件，不为每条事件查询完整 run。终态事件触发一次授权结果读取；断线按 1/2/4/8/15 秒退避，先补读所有事件页，再从最新顺序号订阅同一个 run。25 秒没有事件/心跳时也会补读重连；补读请求整体 15 秒超时，切换记录时中止请求。不会重提问题或触发模型重跑。 |
| `frontend/src/features/runs/runProgress.ts`、`App.vue` | 顺序去重、只用最新 attempt 的事件呈现进度，避免恢复执行时混入旧轮次；切换记录/知识库、退出、卸载时清理订阅和定时器，丢弃旧请求返回。取消按钮显示请求中状态，并防止旧取消响应覆盖新记录。 |

## 取消时实际发生什么

点击取消后先显示“正在请求取消”，后端确认取消后停止后续节点和发布。已有同步模型 HTTP 请求不会被远端立即撤回，它可能继续执行、计费，返回后也不能发布答案。界面明确说明这点；本轮没有改变外部写操作的派发、审批或结果未知处理。

## 代价和边界

- 每个节点和查询增加少量持久化事件；SSE 从约 1 秒一次数据库检查调整为 350 ms，降低推送等待但增加读取频率。当前仍为数据库轮询，没有引入消息代理广播。
- 心跳只证明进度连接仍可用，不代表模型正在产生有效答案；等待时长包括排队，界面不承诺预计完成时间。
- 本轮优化等待反馈与连接恢复，没有改模型请求为 token streaming，没有声称首字延迟或总模型耗时下降。需要人工审核时，审核等待仍然存在。
- 不修改实际 `.env`，不触发真实模型付费调用或第三方业务写入；也不修改并行任务维护的分块策略、向量批次和评测配置。

新增后端 `test_streaming_progress.py` 的 6 项测试覆盖：模型调用前已提交阶段、未核验文本不进入 JSON/SSE 进度、终态超过 200 条事件排空与续传、断开后不再查询、取消 attempt 无法开始/发布、字段白名单。现有 API/工作流定向 15 项回归通过。

本次共享工作区完整后端回归：`python -X utf8 -m pytest -q --tb=short`，**266 passed, 4 warnings in 145.34s**；4 条为 Alembic `path_separator` 配置弃用提示。该总数包含同期其他任务，不能全部归为本次流式改动，也不能和定向数量相加。改动文件与最终全仓 Ruff 检查通过；较早一次检查发现的并行分块导入问题已在最终检查消失，本任务没有修改该文件。日志目录为 `tmp/streaming-validation/`。

## 面试怎么讲

“我把进度流和答案发布分开。执行节点先持久化安全的阶段与计数，前端经 SSE 显示；正文仍走核验和原有人工审批。断线按事件序号补读再重连，不重新发起问题。取消后用 attempt 和状态检查阻止后续执行与发布，已发出的模型请求不承诺立即终止。”

可能追问：为什么不用事件数量估算百分比？因为检索补检、模型重试和修订次数不固定，相同事件数量对应的剩余工作差别很大；阶段与已完成查询数更可解释。
