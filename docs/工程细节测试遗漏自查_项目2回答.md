## 逐题回答

### 1. 哪些异常会重试，哪些异常必须停止？

**状态：部分覆盖。** `test_retryable_server_failures_retry_once_with_a_bounded_limit` 覆盖 500/502/503/504，`test_rate_limit_honors_retry_after_within_deadline_and_records_safe_events` 覆盖 429；新增 `test_permanent_http_errors_are_not_replayed` 覆盖 400/401/403/404/422 只请求一次，`test_repeated_retryable_failure_stops_at_configured_attempt_limit` 验证重试上限；`test_read_timeout_is_not_replayed_because_completion_is_unknown` 覆盖读超时不重放，`test_expired_task_deadline_blocks_provider_request` 覆盖截止时间前置停止。认证失败、权限不足、业务拒绝和各层同时重试的真实请求计数仍没有完整注入。

仍需在端到端故障注入中同时记录网络错误、Provider attempt、任务 attempt、最终状态和费用，确认上层恢复不会把永久错误再次提交。

### 2. 多层重试叠加后，请求总量和耗时是否仍有上限？

**状态：部分覆盖。** Provider 配置允许 0–2 次额外重试（默认 1 次），工作流有模型调用、Token、时间和检索轮次预算；`test_repeated_retryable_failure_stops_at_configured_attempt_limit`、`test_retry_reserves_budget_and_cannot_hide_unknown_usage`、`test_retry_blocked_at_same_call_limit`、`test_recovery_keeps_original_wall_clock_deadline` 覆盖部分边界。没有把 HTTP 重试、工作流补检、Celery 租约恢复和人工重试同时触发，测出端到端总请求数和墙钟上限。

补测应固定一个持续失败依赖，分别打开每一层重试，记录每层次数，验证总量是可计算的有限上界而不是各层上限相乘后失控。

### 3. 退避、抖动和 Retry-After 是否遵守剩余时间预算？

**状态：部分覆盖。** Retry-After、HTTP 日期解析、指数退避、随机抖动和剩余 deadline 已有实现；`test_retry_after_is_a_minimum_and_backoff_jitter_is_bounded`、`test_retry_after_http_date_and_invalid_value_are_handled`、`test_retry_after_beyond_task_deadline_returns_without_replaying` 已通过，`test_cancelled_during_backoff_does_not_start_next_request` 验证退避取消不会发起下一次请求。仍没有并发失败时验证请求实际错峰的测试。

仍需用并发客户端验证真实请求错峰，并把 Provider、任务恢复和队列重投合并测出端到端总请求上限。

### 4. 外部写操作超时但结果未知时，会不会重复执行？

**状态：已覆盖（本机 MCP）/待验证（真实供应商）。** `test_write_timeout_unknown_no_replay_and_manual_receipt` 和 `test_lost_receipt_stays_non_replayable_and_stale_execution_becomes_unknown` 验证服务端可能已写入但回执丢失时标为 `unknown`，后续不能盲目重放；本机 MCP fixture 也验证了幂等键和延迟写入。没有真实第三方服务的幂等键不可用、状态查询失败和实际回执核对证据。

补测应在独立测试资源中分别验证“已写入/明确未写入/状态未知”，只有有可靠状态或供应商幂等保证时才允许继续，未知结果必须保留人工核对状态。
