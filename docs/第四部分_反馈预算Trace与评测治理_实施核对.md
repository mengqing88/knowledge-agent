## 十三、拒绝反馈、知识发布与失败回归

### 66. 用户拒绝时，应该问清什么？

**旧行为与问题：**`ReviewRecord` 仅存 answer_id、用户和自由文本，“不满意”无法区分措辞偏好和事实错误，也没有读取反馈的 API。

**已实施：**`schemas.ReviewCreate` 接收用户选择的 preference/factual_error/execution_failure/missing_scenario/requirement_change/unable_to_complete/unclear；原话保留空白，禁止全空白。`main.review` 在鉴权后先保存原话、分类、答案内容哈希和可选幂等键；`unclear` 返回具体澄清选项，绝不猜分类。新增本人反馈 GET，前端接入分类选择和已保存反馈回看。

**方案与取舍：**规则/模型自动分类可能把偏好误判成技术缺陷，且增加调用；用户选择加“原因待澄清”更符合本地最简版。分类来源明确为 user_selected/unclassified，不是已证明的根因。历史反馈不覆盖答案，也不直接进入检索知识。已验证原话、幂等冲突、空白拒绝、跨用户不可见以及无新增模型调用；浏览器端到端尚未验收。

**代码修复扩展：**拒绝补丁时除保留原话外，还记录用户选择的反馈类别、可能根因层和未确认事项。根因层只代表审核者的当前判断，不由模型自动归因；拒绝记录可以在任务详情重新读取。

### 67. 拒绝经验怎样变成长期回归用例？

**当前与建议：**原话已持久化；没有实现自动生成测试、隔离双向复现、人工发布正式回归集的整条闭环。可选个人记忆中的“失败经验”也不等于已验证技术反例。本轮不把用户偏好转成技术断言，不自动执行生成代码。

**推荐流程：**原反馈 → 脱敏副本 → 人工明确目标行为与旧版本 → 候选用例及来源哈希 → 隔离运行 → 人工核查反例有效 → 带版本发布。修缺陷时旧版因目标缺陷失败、修复版通过；判断补丁破坏正常行为时基线通过、拒绝补丁失败。依赖缺失、语法错误、收集失败和无关断言不算有效反例。

**取舍与验证：**先由人工编写有行为断言的回归，比立即引入生成/执行/审核平台简单。失败候选保留原反馈、测试内容、运行环境、标准输出/错误和失败原因，不能发布为成功知识。本轮预算/未知 usage 的回归是人工编写的控制测试，不是已跑通自动反馈闭环。

### 68. 怎么避免审核了 A，却发布了 B？

**现状（第四部分收尾时）：**知识库答案当时在确定性引用/语义核验后发布，每 run 仅一版；用户反馈绑定 answer_id 和答案完整序列化内容的 SHA-256。反馈记录“评价了哪一版”，不代表人工批准。答案发布审批随后在第一部分扩展中实现，当前门禁见[第一部分实施核对](第一部分_协作输入与工作流基础_实施核对.md)。可选代码修复/外部写模块有各自的补丁哈希或操作 digest，属于独立扩展。

**方案比较：**只绑定任务 ID 无法识别内容更改；绑定完整对象的版本/哈希并在提交前重算可拦截旧页。若将来做失败回归发布，批准对象至少覆盖原反馈、测试全文、验证命令/环境与报告；改其中任意一项使旧批准失效。并发修改以服务端版本比较处理，不能只禁用前端按钮。

**本部分当时的边界：**没有新增答案审批或回归集发布状态机；不能因反馈有哈希就声称整套人工审核已完成。答案审批后来另行实现；回归集发布状态机仍未实现。外部工具授权的 digest 检查由对应扩展测试，不以问答反馈测试替代。

代码修复审核另有 `verification_sha256`，覆盖基线、任务目标、选中文件、摘要、补丁哈希、固定测试命令、Docker 镜像 ID、测试文件清单、退出码和完整输出哈希；审核时重新校验。`CodeRepairReview.bundle_sha256` 绑定接受/拒绝记录，和 `artifact_sha256` 补丁哈希分开，避免把补丁版本误当成测试证明。

### 69. 修复应该落在哪一层？

**本次归因：**无 usage 被当零是适配器与统计契约问题，因此在 Provider 标记未知、数据库保存预留、API 显示 null、评测汇总识别未知；HTTP 重试绕过累计预算落在 Provider 发送边界与 Workflow 预留；含糊反馈分类落在输入/持久化与前端选择，不加模型提示词猜根因。

**选择理由：**缺原始资料应补知识，已有资料未进入上下文应查检索/重排；工具误用查 Schema/适配器；权限落到后端；遗漏恢复/验收步骤查状态流。每层解决不同问题，不能靠一条“请准确回答”统一兜底。本次沿同一复现检查旧行为和新行为，代价为每次请求前后新增持久化及保守估算。

### 70. 后续服务失败，会不会丢掉拒绝记录？

**已实施并验证：**反馈 API 在一个数据库事务保存后返回；处理反馈不调用聊天或向量服务，也不触发重排、发布和索引。因此后续模型故障不能撤销已提交反馈；重复请求同幂等键回同一记录，换内容返回 409。GET 可回看原话，跨用户和被撤权访问仍经原答案归属检查。

**未实现的部分：**没有反馈处理后台队列、向量化或自动补做。未来若加候选生成，先保存原反馈，再按稳定 feedback_id 分 pending/needs_human/validated/published/failed；正文落盘、索引可用、回归发布必须是不同状态。不能把当前“已保存”称作“已自动学习”。

代码修复拒绝采用先提交审核记录和 `cleanup_pending`，再回滚 worktree 的顺序。清理失败时保留原始理由并记 `cleanup_failed`，页面可单独重试清理；清理成功记 `restored`。这是为避免清理与数据库提交跨资源事务导致反馈丢失，不代表拒绝反馈已经变成回归用例。

## 十四、请求预算、并发与缓存

### 71. 能否在发请求前控制 Token 和费用？

**已实施：**`governance.estimate_tokens` 使用 UTF-8 字节数加固定余量估算；Workflow 请求前锁 run、累计所有 attempt 的已知用量/未知预留、验证单次与总额度、按剩余额度缩小输出上限，先写 `ModelCall(status=started)` 和开始事件，事务成功才发送。Provider 另有聊天输入/Embedding 单条或至多 16 条批量输入护栏。

**重试：**Provider 在下一次 HTTP 发送前调用 `before_retry`；Workflow 保留前一次完整预留并标记未知，再为新尝试建账，最终 usage 只结算当前尝试。复核曾发现缩小重试输出额度后将未知预留从 7448 错记为 2552；行为回归已复现，现保留原预留，不因重试缩额减少先前潜在消耗。结构解析失败保留已收到 usage；无完整 usage、超时或进程崩溃记未知，不计为零。

**费用：**可选 `MAX_RUN_COST`，需模型当前价格、币种和价格来源；缺价格时拒绝启用该费用预算。成本按输入/输出每百万 Token 价格估算，未知调用保守保留预留；未配置价格时 cost=null。默认不开金额上限，不假造供应商价格。优先采用保守护栏，未引入供应商 tokenizer/账单查询；估算误差、HTTP 框架开销及供应商计费差异意味着不是精确硬账单上限。文档入库有单批输入护栏，但不属于 question run 总额度，尚无跨文档全局金额账本。

### 72. 预算耗尽后，返回部分、降级还是请求继续？

**已实施：**时间、调用次数、Token、费用、单次输入与检索轮数分别保留 `budget_category`；发布仅保留已完成相应检查的论点，完整模式未被 Verifier 批准的草稿不能因额度不足直接发布。缺口使用对应中文标签；没可发布论点则 insufficient，不伪装 supported。

**边界：**关键词降级来自 Embedding 瞬时故障策略，不因预算不足绕过核心验收。钱和 Token 不随 checkpoint/attempt 重置；从首次 started 计算 wall-clock，恢复等待也计入，排队前等待不计。停止后仍执行持久化/心跳线程收尾，已经发送的远端请求不能撤回。没有“追加预算继续”按钮，也没有人工等待中续算语义；对外部操作不能把预算耗尽当成远端未执行。

### 73. 追加预算怎样做到不重置历史、不重复加钱？

**现状：**不支持原 run 追加/续跑；已有的 replay 是新 run，有新清单和预算，会再次调用模型。本轮修复的是恢复不能清空已用预算，不能称为追加预算已实现。

**方案：**简单新建 run 最易解释但会重复检索/付费；真正续跑需要 BudgetGrant（run、发起用户、原因、各类增量、幂等键、创建时间）、初始清单不变、行锁内同时写额度追加与状态。稳定幂等键应将重复点击/响应丢失合并，同键不同内容返回冲突。累计可用额度=初始+grant−已耗/预留，不能覆盖初始值。

**续跑前提：**确认归属、当前角色、有效快照、明确恢复节点、旧 worker 停止和环境清理；存在未知外部结果先核对，不能直接重放写操作。初次实现与测试成本较高，目前没有实际任务要求追加，保留设计而未添加状态机。

### 74. 并行、排队和领取任务怎样配合？

**已有：**第三部分 `capacity.py` 通过 `workload_gate` 串行准入/领取；默认待处理 40、每用户问题 3、有效租约并行任务 2、恢复 attempt 3。Celery prefetch=1；Windows worker 默认 solo，不预领大量任务。这里引用第三部分的控制测试，不将其成果重复计数。

**推荐：**多个 run 可由不同 worker 处理，内部 Planner→检索/重排→分析→核验有依赖，保持顺序。独立查询可并行，但当前检索还会共享证据去重、事务和预算，直接 gather 会扩大锁冲突及供应商突发量；先保留顺序，在真实 PostgreSQL/Redis 与模型配额压测后再定并发。新增请求预留是 run 行锁保护，不能只靠进程内计数。未知并发实际 QPS/P95 不填成绩。

### 75. 哪些结果可以缓存，怎样失效？

**现状与判断：**没有新增业务缓存。已有文档内容哈希、索引版本与快照不是模型响应缓存；`get_settings` 的 lru_cache 只是配置读取。当前缺相同请求的真实复用频率与收益证据，先不增加缓存服务。

| 对象 | 将来可用的缓存键与失效依据 |
| --- | --- |
| Embedding | 文本内容哈希、Provider/模型/维度/revision、估算/输出契约版本；权限仍在取用时检查 |
| 检索 | 用户/库/权限身份、快照和索引版本、查询、路由/重排参数；撤权或当前版本变化必须重新鉴权 |
| 代码分析 | 可选代码任务的确切源码树/未提交内容、分析器与配置；不能只用路径或 commit |
| 模型输出 | 规范化完整输入、提示词/Schema、模型/参数、资料版本与用户/记忆权限；成本和新调用身份不能伪装历史 |
| 外部工具 | 只有明确只读且有业务 TTL/版本证明的结果；当前外部状态、批准、未知写结果不能据缓存认定 |

TTL 只作补充，不能代替内容/权限版本。实施后需测命中率、端到端收益与过期错误；仅写入缓存不能证明优化有效。

## 十五、配置冻结、Trace 与环境诊断

### 76. 一次任务的完整配置能否查出？

**已实施：**创建 run 时保存原始问题身份、最多四条前问、快照哈希、模型/服务身份、生成与预算/重试参数、价格来源、角色提示词全文和 Schema、应用文件/锁文件哈希、主要已安装包版本、记忆上下文及总 manifest 哈希。trace 和 recording 可读取；执行前核对清单、模型服务、应用源码、锁文件、主要依赖与材料身份，变化则拒绝旧 run，不能静默切换。

**取舍：**使用显式允许字段，密钥只记环境变量引用、地址只记身份哈希；无凭据版本系统。此清单覆盖知识库问答，不冻结可选 MCP 运行时发现的全部工具权限，也不保存 Python/系统依赖镜像、源码归档或模型真实权重版本。授权/记忆删除仍由当前后端规则执行，不能拿冻结清单维持已撤销权限。严格代码身份检查会使更新后排队 run 失败，需重新创建问题；这是可见的限制。

### 77. 记录回放与重新执行一样吗？

**已实施：**新增 `GET /api/question-runs/{id}/recording` 只读保存的 run、全部事件、trace，返回未完成调用 ID，不调用模型/工具，不补造缺失响应。历史旧记录可能没有开始事件或清单，明确给限制。原 `POST .../replay` 继续创建新运行，本次保留原 parent_run_id，使追问重新执行仍有前问；`replay_of` 创建时纳入冻结哈希和幂等内容比较，复用原请求 key 会返回冲突，不能把原 run 改成重跑。

**选择与边界：**读取记录适合定位当时的输入、证据选择和状态；新执行适合复测当前配置，可能再次付费且输出不同。界面原“重试”继续新执行，recording 先以 API 提供，不伪称有时间轴播放器。权限和当前可用版本仍约束新执行，历史只读不保证任意旧快照可重跑。HTTP 未完成、缺记录原样显示未知。

### 78. 有 commit/哈希就能重建环境吗？

**不能。**当前目录没有 Git 元数据，不擅自 init；应用/锁文件 hash 只作识别，不能恢复丢失内容。已有 uv.lock 和 package-lock，Compose 仍是镜像标签，未固定/归档 digest；供应商模型为别名。没有自动环境重建，清单明确 `hashes_only_no_source_or_image_archive`。

**推荐：**应用源代码与未提交差异独立归档、保存可获取依赖包与镜像 digest、系统/Python 版本、数据库/对象存储备份和迁移基线，另做净环境重建演练。服务代码版本与可选待修复仓库 checkpoint 分开。代价为存储和演练维护；本轮没有借“可复现”扩大承诺。

### 79. 完整 Trace 应记录到哪层？

**已实施/整合：**run/request_id → attempt → 节点事件 → ModelCall ID → Provider HTTP 尝试/重试 → 检索与来源 → 答案。调用发送前落 started/预留，成功或失败后保存响应摘要、usage 已知位/供应商 ID/耗时并结束；崩溃留下 started。HTTP 重试另有未知预留，节点耗时不与内部请求耗时简单相加。

**已有与未有：**第三部分提供 HTTP 尝试/降级事件、规则脱敏；可选 MCP/外部操作有独立回执/审计。主链不是 ReAct 任意工具循环，没有不可见模型思维输出，也没有集中监控告警。调用前写库失败会阻止对应请求，已加入故障注入断言；远端完成但本地收尾失败仍可能是未知，不能由审计声明回滚。规则脱敏无法识别所有未知秘密，业务摘录仍受本人/库权限保护。

### 80. 端口启动失败与业务失败怎样区分？

**本轮未遇到新的 bind 错误，不推测端口原因。**实际 Docker 错误是命名管道 `dockerDesktopLinuxEngine` 不存在，是 Engine 连接失败，不能说成 55432/56379 占用。当前 API/前端默认仍为 8000/5174，数据库/Redis 映射 55432/56379。

**诊断顺序：**记录实际 WinError/OSError、绑定地址及进程是否退出 → `Get-NetTCPConnection -State Listen` 查对应 PID → 用 `netsh interface ipv4 show excludedportrange protocol=tcp` 只读核对系统保留范围 → 检查 backend 启动、Vite proxy 与请求 URL 一致。未监听可能是未启动而非占用；API 已启动后模型 HTTP 超时属于业务依赖故障。当前无证据需要换端口或修改防火墙/权限，因此未操作系统配置。

## 十六、可验证评测、真实验收与版本治理

### 81. 正式评测要求 Markdown

**已编写：**`evaluation/评测要求.md` 定义开发/冻结集、正常/边界/恶意/故障覆盖、分层归因、人工评分、对照、分母、P95 与产物。控制集要求已定义不变量全通过、安全硬失败为零；实际质量/费用/延迟阈值需在正式实验前填写冻结，目前没有被确认的效果目标。

**已改工具：**运行器接登录（不回显密码或环境会话令牌）、本机禁用代理环境继承；轮询超时/失败仍尝试取消并抓 trace，取消失败明确 unknown。汇总使用 manifest 全题分母，缺文件计失败、未知/重复题号报错、非终态不算完成；已知 Token 小计与未知次数分开，增加含失败尝试的 P50/P95/max/观测数。合并的价格汇总要求全部有估价及价格来源、同一币种；未知或混币种不相加。

### 82. Top-5、修复成功数、回归通过率怎样算？

**定义与实现：**规范仍区分 Hit@5 与 Recall@5。汇总器提供探索性的首查询 Hit@5：仅取每道有 `relevant_chunk_ids` 标签题的首 attempt、首轮、第一条请求 top 5；分母固定为全部有标签题，缺失计未命中并单列。不同子问题与补检不会被合成大于 5 的候选集，也不通过增加查询稀释失败。标签仍是问题级，不等于完整子查询检索评测或 Recall@5；正式实验前仍需独立人审和口径冻结。

**适用边界：**本项目主流程回答问题，不做 30 个代码修复 benchmark；可选代码任务测试通过也不等于独立隐藏验收的修复成功。回归通过率须列测试用例总数、失败/超时/跳过，或明确是候选产物分母。问答三模式共享混合检索，不能冒充 RAG 开关修复对照或纯检索三路实验。

**结果：**82%、16/30→22/30、96% 在原清单是示例；无证据则不能采纳。本轮新增确定性测试数和 P95 汇总能力不产生任何这些数字。
